# 10. 실시간 랭킹 — 설계 결정

Kafka Consumer가 집계한 `product_metrics`(MySQL)를 바탕으로 Redis ZSET에 랭킹을
적재한다. 적재 코드를 쓰기 전에 먼저 못 박아야 하는 정합성·설계 결정을 정리한다.

## 전제 — Redis 랭킹은 "파생 뷰"다

진실의 원천은 `product_metrics`(MySQL), Redis ZSET은 이를 빠르게 보여주는 **파생
캐시**다. 게다가 랭킹 키는 TTL이 짧아 어차피 버려지는 데이터다.

> **커머스 비유**
> - **판매 원장**(MySQL): 정식 기록. 잘못되면 트랜잭션으로 되돌린다.
> - **베스트셀러 전광판**(Redis 랭킹): 매장 입구에 건 실시간 인기 순위판. 파생물이라
>   조금 틀려도 되고, 틀리면 원장 기준으로 다시 그린다.

이 관점이 아래 모든 결정의 기준이다 — **랭킹은 약간 틀려도 치명적이지 않고, MySQL
기준으로 재구성(rebuild)해 자가 치유한다.**

---

## 결정 1 — 이중 쓰기 (MySQL + Redis 정합성)

이벤트 하나를 원장과 전광판 두 곳에 적어야 하는데, 한쪽만 적히고 끊길 수 있다. 원장은
트랜잭션으로 되돌리지만 **전광판은 되돌릴 수 없다** — 한 번 올린 점수는 롤백이 안 된다.

| 실패 상황 | 결과 |
|---|---|
| 전광판 먼저 반영 → MySQL 커밋 실패 | 전광판에만 점수 남음(롤백 불가) → **과다 집계** |
| 전광판 반영 실패 → 예외로 롤백 | 메시지 재시도 → 부분 반영 위험 |

### 선택지

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 커밋 후 best-effort + 재구성** | 커밋 성공 후에만 `ZINCRBY`(afterCommit). 실패 시 로그 + rebuild로 자가 치유 | 단순, MySQL 정합성 유지 | 순간적 과소 집계 가능 |
| B. 트랜잭션 내 동기 반영 | `@Transactional` 안에서 `ZINCRBY` | 직관적 | 커밋 실패 시 과다 집계(롤백 불가), Redis 장애가 집계 전체를 중단 |
| C. Redis 반영 추적으로 정확히 1회 | "Redis에 반영했는지"를 별도 추적 | 과다·과소 없이 정확 | 추적·경합 관리로 복잡도↑, 과투자 |

### 결정

> **A — 커밋 후 best-effort + 재구성**

파생 뷰에 강한 즉시 일관성을 맞추는 건 과투자다.
- **B 기각**: 커밋 실패 시 과다 집계로 남아 rebuild 없이는 자가 치유 불가하고, Redis
  장애가 집계 파이프라인 전체를 멈춰 세운다(파생 캐시가 본체를 볼모로 잡음).
- **C 기각**: 곧 버려질 순위판을 위해 추적 테이블·경합 관리를 또 만드는 건 과투자.

**A의 두 조건:**
1. **순서는 MySQL 커밋 후 Redis**(afterCommit). 실패해도 **과소 집계**로만 끝난다 —
   과소는 rebuild로 채우지만, 과다는 어디가 틀렸는지 알 수 없다.
2. **rebuild 경로 확보.** best-effort로 실패한 점수를 MySQL 기준으로 다시 채울 수단.
   콜드 스타트 Carry-Over 스케줄러와 같은 machinery다.

## 결정 2 — 멱등성 (재처리 시 ZINCRBY 중복 방지)

Kafka는 같은 메시지를 재배달한다(컨슈머 재시작·리밸런싱·재시도). **같은 주문 전표가 두
번 접수**되는 셈이다. 원장은 `event_handled`("처리한 전표 대장")로 이미 막지만,
전광판의 `ZINCRBY`는 "현재값에 더하기"라 두 번 부르면 그대로 **두 배**가 된다.

### 결정

> **`event_handled` 게이트 하나가 MySQL·Redis 멱등성을 동시에 책임진다.**

```
1. @Transactional
   - event_handled 있으면 → return (아무것도 안 함)
   - 없으면 → event_handled 기록 + product_metrics 갱신 → 커밋
2. 커밋 성공 후 → Redis ZINCRBY   (afterCommit)
```

**핵심 규칙**: afterCommit 등록을 dedup을 통과한 "새 이벤트" 분기 안에서만 한다. 이미
처리된 이벤트면 Redis도 건드리지 않는다.

| 재배달 상황 | 결과 |
|---|---|
| 이미 처리된 이벤트가 또 배달 | 게이트가 skip → **중복 없음** |
| 커밋 후 Redis 직전 크래시 → 재배달 | 게이트가 skip → 이 건 누락(**과소 집계**) |

과소 집계는 결정 1에서 수용한 트레이드오프이며 rebuild로 보정한다. 좋아요 취소(-0.2)의
이중 차감도 같은 게이트가 막는다. 별도 "Redis 반영 추적" 테이블은 만들지 않는다(결정
1에서 버린 C안).

## 결정 3 — TTL (언제 EXPIRE)

날짜별 키 `ranking:all:{yyyyMMdd}`는 며칠 뒤 자동 삭제돼야 한다(안 지우면 날짜별
전광판이 매일 쌓여 메모리 잠식). 그런데 `ZINCRBY`는 점수만 더할 뿐 만료를 안 걸어준다.

### 선택지

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **매 이벤트마다 EXPIRE 갱신** | `ZINCRBY` 후 항상 `EXPIRE key 2d` | 만료 항상 보장, 단순 | 이벤트마다 명령 1회 추가 |
| 키 최초 생성 시 1회만 | 키가 새로 만들어질 때만 EXPIRE | 명령 최소화 | "처음"을 잡는 경합 처리 필요 |

### 결정

> **매 이벤트마다 EXPIRE 갱신** (ZINCRBY + EXPIRE를 Lua/파이프라인으로 묶음)

- **자가 치유가 공짜**: "최초 1회만"은 그 한 번의 EXPIRE가 실패·경합으로 누락되면 키가
  영영 안 지워진다(메모리 누수). 매번 걸면 이번에 실패해도 다음 이벤트가 다시 건다.
- **단순**: "방금 새로 생긴 키인가?" 판단·경합이 없다.
- **비용 거의 0**: Lua로 묶으면 왕복 1회이며 원자적.

날짜 고정 키라 슬라이딩 윈도우 문제도 없다 — 오늘 키의 마지막 이벤트는 늦어야 23:59,
+2일까지 유지되어 요구사항 "이전 날짜 랭킹도 정상 조회"를 오히려 확실히 만족한다.

## 가중치 산정

**문제 — 자릿수가 다르다.** 요구사항 예시(점수 = Weight × Score)를 그대로 쓰면 주문
항만 자릿수가 폭발한다. 15만원 1개 = `0.6 × 150000 = 90,000`, 조회 한 번 = `0.1`.
**주문 1건이 조회 90만 번**과 맞먹어 조회·좋아요가 노이즈가 된다(롱테일).

### 결정 — 주문 금액에 log 정규화

```
조회   score += 0.1
좋아요 score += 0.2   (취소 시 -0.2)
주문   score += 0.6 × log10(1 + price × amount)
```

가중치 0.1/0.2/0.6은 요구사항 예시값(상대적 중요도)을 그대로 쓰고, 주문 금액만
log10으로 누른다.

**왜 log인가** — 값이 10배 될 때마다 +1이라, 곱셈으로 벌어지는 차이를 덧셈으로 눌러준다.
1천원~1천만원(1만 배)이 `3.0~7.0`(약 2.3배)로 압축돼, 비쌀수록 유리하되 점점
완만하게(diminishing returns) 오른다. 가중치만 낮추면 여전히 선형이라 지배 구도가 안
바뀌고, 상한선(cap)은 특정 금액에서 뚝 끊기는 절벽이 생긴다. `log(1 + 금액)`으로 감싸는
건 0원이면 0점이 되게 하고 음수·발산(`log(0) = -∞`)을 막기 위함이다.

- **double 그대로**: 우리는 순서만 필요해 부동소수점 미세 오차가 순위를 안 뒤집는다 →
  정수 스케일링 불필요.
- **설정화**: 0.1/0.2/0.6을 `ranking.weight`로 빼 Nice-to-Have "실시간 Weight 조절"로
  자연스럽게 잇는다.

## 콜드 스타트 완화 — Score Carry-Over (일간, 확정)

일간 키는 자정에 0점에서 시작한다. 새벽엔 트래픽이 적어 **점수 몇 개가 순위 전체를
좌우** → 지나가던 한 명의 조회(+0.1)가 곧장 1등이 되는 랜덤 순위판이 된다.

> **커머스 비유**: 자정에 베스트셀러 전광판을 백지로 갈면, 새벽 첫 손님의 클릭 하나가
> 1등이 된다. 그래서 자정 직전 오늘 순위를 **옅게 밑그림**으로 깔아둔다. 오늘 판매가
> 쌓이면 밑그림은 묻혀 사라진다.

```
내일 키 시작 점수 = 오늘 점수 × 감쇠계수(예: 0.1)
```

**"어제 랭킹 조회"와 다르다** — 가져온 어제 점수는 보여줄 데이터가 아니라 **오늘의
출발점(prior)**이다. 어제 조회(`?date=어제`)는 확정·불변 순위를 그대로 노출하는 별개
기능(이미 완료)이고, Carry-Over는 오늘 판의 초기 밑그림이라 오늘 이벤트가 쌓이면 덮인다.
**감쇠하는 이유**: 어제 1등을 그대로 넘기면 관성으로 오늘도 1등이라 신흥 인기가 못
올라온다(고인물). 감쇠는 출발선 어드밴티지만 주고 승부는 오늘 이벤트로 가린다.

### 결정

> **소스 = 오늘 Redis Top-N / 쓰기 = ZADD(절대·멱등) / 위치 = commerce-streamer /
> 감쇠·N 설정화 / 락 없음**

- **소스는 오늘 Redis 키**: MySQL은 누적 카운트라 일자 구분이 없다. 일간 점수를 가진
  유일한 곳이 오늘 ZSET.
- **Top-N만**: 새벽엔 상위권만 의미 있어 `ZREVRANGE 0 N-1 WITHSCORES`로 상위 N개만.
- **ZADD 절대값**: 23:50엔 내일 키가 비어 있어 안전하고, 두 번 돌거나 인스턴스가
  여럿이어도 결과 동일(멱등) → 별도 락 불필요.

```
@Scheduled(cron="0 50 23 * * *", zone="Asia/Seoul")
carryOver():
  top = ZREVRANGE todayKey 0 (N-1) WITHSCORES
  if top.isEmpty(): return                         // 첫날·무트래픽이면 스킵
  for (member, score) in top: ZADD tomorrowKey (score × DECAY) member
  EXPIRE tomorrowKey 2d
```

## 시간 단위 실시간 랭킹 (Nice-to-Have, 확정)

요구사항 Additionals의 "1시간 단위 랭킹" — **"지난 1시간 인기 상품"**을 만든다. 앞선
결정 1·2·3(best-effort·멱등·TTL 매번 갱신)을 그대로 재사용하는 게 기조다.

### 전제 — "실시간 = 지난 1시간"이 구조를 결정한다

"실시간"을 **"지금부터 뒤로 60분(슬라이딩)"**으로 정의하는 순간, 시간을 잘게 쪼개는
구조가 강제된다. 시간은 연속적이라 매 순간 "정확히 60분 전부터 지금까지"를 다시
계산하는 건 비싸기 때문이다.

> **커머스 비유**: 매출을 **1분마다 집계함**에 나눠 담는다. "지난 1시간 인기"를 물으면
> 최근 60개 집계함을 꺼내 합친다. 1분 지나면 맨 앞 함 하나가 빠지고 새 함 하나가 들어와
> 창이 자연스럽게 밀린다.

이 정의에서 결정 6가지가 따라 나온다.

### H1 — 윈도우 방식 (텀블링 vs 슬라이딩)

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| 텀블링(정각 기준) | `ranking:hourly:{yyyyMMddHH}` 한 키, 정각마다 백지 | 일간과 동일 구조, 구현 거의 공짜 | **콜드 스타트 24배 악화** — 11:01엔 1분치로만 순위 |
| **슬라이딩(롤링 60분)** | 분 버킷을 모아 "직전 60분" | 정각 끊김 없음, 콜드 스타트/톱니 자연 완화 | 한 키로 안 됨 → 시간 양자화 필요 |

> **슬라이딩(롤링 60분)** 채택. 텀블링은 매 정각 백지라 콜드 스타트를 하루 24번 겪는다.
> 슬라이딩의 대가인 "시간 양자화"가 바로 이 과제의 핵심("양자화는 왜 필요한가")이다.

### H2 — 버킷 크기 (양자화 단위)

| 버킷 | 합칠 개수 | 창 밀림 단위 | 성격 |
|---|---|---|---|
| **1분** | 60개 | 1분 | 가장 실시간스럽고 직관적 |
| 5분 | 12개 | 5분 | 프로덕션 흔한 절충 |
| 10분 | 6개 | 10분 | 가볍지만 계단 티남 |

> **1분 버킷** 채택. 키: `ranking:min:{yyyyMMddHHmm}`.

- "지난 1시간 = 최근 60개"로 딱 떨어지고, 일간 키 `ranking:all:{yyyyMMdd}`에 시·분만
  붙인 확장이라 새 개념이 없다.
- 살아있는 키 60~120개, 각 함엔 그 1분 이벤트만 담겨 대부분 작다 → 60개 합산 순식간.
- 버킷을 굵혀도 "지금" 순위는 계속 변한다(새 이벤트는 현재 함에 쌓임); 양자화 영향은
  **꼬리(옛 함이 언제 빠지나)**뿐이다. 5/10분은 조회 QPS가 셀 때의 선택지 →
  **윈도우·버킷 크기는 설정화**해 나중에 한 줄로 바꾼다.

### H3 — 조회 집계 방식 (언제 60개를 합치나)

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| A. 조회 시 합산(on-read) | 요청마다 최근 60개 `ZUNION` | 항상 최신, 스케줄러 없음 | 비용이 **QPS에 비례**, 같은 답 매번 재계산 |
| **B. 스케줄러 사전 합산** | 1분마다 `ZUNIONSTORE` → `ranking:hourly:current`, 조회는 그 키만 | 조회가 단일키 읽기, 비용이 QPS 무관 | 최대 1분 stale, 스케줄러 필요 |
| C. on-read + 결과 캐시 | on-read 후 몇 초 캐싱 | 무트래픽 시 계산 안 함 | 캐시 만료 경계 복잡 |

> **B — 스케줄러 사전 합산** (`ranking:hourly:current` 롤링 키).

- "지난 1시간 인기"는 누가 봐도 같은 답이라, 합산을 1분 1회로 고정해 **비용을 QPS에서
  분리**한다. 조회 폭주에도 안 흔들린다.
- 조회는 단일 키 `ZREVRANGE`라 기존 일간 조회 로직·DTO를 재사용.
- `ZUNIONSTORE`는 덮어쓰기라 멱등 → 락 불필요. 롤링 키에 짧은 TTL(2분)을 걸면 스케줄러가
  죽어도 낡은 판을 오래 노출하지 않고 자연 만료(자가 치유).
- 1분 stale은 "지난 1시간"에선 안 보이는 오차라 수용.

### H4 — 시간 감쇠 (오래된 버킷을 흐리게?)

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 감쇠 없음(flat)** | 60개 균등 합산 | 단순, "지난 1시간" 정의에 충실 | 밋밋, 버킷 빠질 때 미세 절벽 |
| B. 시간 감쇠 | 오래된 버킷일수록 작은 weight(`ZUNIONSTORE WEIGHTS`) | 실시간다움 + 절벽 완화 | 감쇠식·계수 튜닝, 복잡도↑ |

> **A — 감쇠 없음(flat)**. 감쇠 계수를 얹을 자리만 설정으로 열어둔다.

- 1분 버킷이면 함 하나가 윈도우의 1/60뿐이라 빠질 때 절벽이 이미 작다.
- 슬라이딩 자체가 최신성을 준다(오래된 건 60분 뒤 창밖으로 퇴장).
- 이미 H3에서 1분마다 `ZUNIONSTORE`를 돌고 있어, 나중에 버킷별 weight만 얹으면 감쇠는
  거의 공짜로 붙는다. Must-Have에서 감쇠식 튜닝까지는 과투자.

### H5 — write 경로 (이벤트를 버킷에 어떻게 담나)

> **기존 afterCommit best-effort 경로에 분 버킷 쓰기를 하나 더 얹는다** (결정 1·2·3 재사용).

```
커밋 후(afterCommit):
  ZINCRBY ranking:all:{today}        + EXPIRE 2d   (기존 일간)
  ZINCRBY ranking:min:{yyyyMMddHHmm} + EXPIRE 2h   (신규 분 버킷)
```

`event_handled` 게이트가 일간·분 버킷 양쪽 중복을 동시에 막고, 실패는 과소 집계로만 끝나
다음 이벤트/스케줄러가 보정한다. 분 버킷 TTL은 윈도우(1h)에 여유를 더해 2h면 충분.

### H6 — API 노출 방식

| 방식 | 예시 | 장점 | 단점 |
|---|---|---|---|
| A. 파라미터 | `GET /api/v1/rankings?period=hourly` | URL 통합, 토글 쉬움 | `period=hourly`면 `date` 무의미 → **무효 조합**, 컨트롤러 2역할 |
| **B. 별도 엔드포인트** | `GET /api/v1/rankings/hourly` | 계약이 정직(무효 조합 불가), 메서드 단일 목적 | 엔드포인트 2개, DTO 약간 중복 |

> **B — 별도 엔드포인트** `GET /api/v1/rankings/hourly?page=&size=`.

일간은 날짜로 고르고(`?date=`) 시간은 롤링 스냅샷 하나라 조회 모델이 다르다. A는
`period=hourly`일 때 `date`가 언제 유효한지 모호해지는 무효 조합이 생긴다. B는 그
모호함이 원천적으로 없고, 응답 DTO는 Facade/DTO 공유로 중복을 없앤다.

### 콜드 스타트는 자동 해소된다

일간에서 carry-over로 따로 풀던 "매 정각 백지"가 시간 랭킹에선 **H1(슬라이딩) 선택만으로
사라진다** — 정각에 판을 갈아엎지 않고 창이 1분씩 밀리는 구조라 리셋 시점 자체가 없다.
서버 최초 기동 직후 빈 창은 최대 1시간이면 채워지므로 수용한다.

### 키 / TTL 요약

| 키 | 용도 | 쓰기 | TTL |
|---|---|---|---|
| `ranking:min:{yyyyMMddHHmm}` | 1분 집계함(원천) | 이벤트마다 `ZINCRBY`(afterCommit) | 2h |
| `ranking:hourly:current` | 사전 합산 롤링 판(조회 대상) | 1분마다 `ZUNIONSTORE` 덮어쓰기 | 2m |

```
@Scheduled(fixedRate=60_000)   // 1분마다
refreshHourly():
  keys = 최근 60개 [ranking:min:{now-59m} ... ranking:min:{now}]
  ZUNIONSTORE ranking:hourly:current 60 keys   // (WEIGHTS 자리 열어둠)
  EXPIRE ranking:hourly:current 2m
```
