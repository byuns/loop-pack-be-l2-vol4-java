# 10. 실시간 랭킹 — 정합성 설계 결정

Kafka Consumer가 집계하던 `product_metrics`(MySQL)를 바탕으로, Redis ZSET에
실시간 랭킹을 적재한다. 본격적인 적재 코드를 작성하기 전에 **반드시 먼저 방향을
정해야 하는 정합성 결정 3가지**를 정리한다. (각 항목의 최종 선택은 이후 하나씩 확정한다.)

## 전제 — Redis 랭킹은 "파생 뷰"다

진실의 원천(source of truth)은 `product_metrics`(MySQL)이고, Redis ZSET은 그것을
빠르게 보여주기 위한 **파생 캐시**일 뿐이다. 게다가 랭킹 키는 **TTL 2일**이라 애초에
버려지는 데이터다.

> 비유: MySQL은 정식 회계장부, Redis 랭킹은 사무실 벽의 화이트보드 순위판이다.
> 화이트보드가 조금 틀려도 회계장부만 정확하면 언제든 다시 베껴 쓰면 된다.

이 관점이 아래 세 결정의 판단 기준이 된다 — **랭킹은 약간 틀려도 치명적이지 않으며,
MySQL 기준으로 재구성(rebuild)해 자가 치유할 수 있다.**

---

## 결정 1 — 이중 쓰기 (MySQL + Redis 정합성)

### 한 줄 요약

같은 사건을 **두 곳(장부·순위판)에 적어야 하는데, 한쪽만 적히고 끊길 수 있다.**

### 쉽게 풀면

이벤트 하나가 들어오면 우리는 두 군데에 기록해야 한다.

- **MySQL `product_metrics`** = 정식 **회계장부** (연필로 씀 → 지울 수 있음)
- **Redis ZSET** = 벽의 **화이트보드 순위판** (유성펜으로 씀 → 깔끔히 못 지움)

문제는, MySQL은 "트랜잭션"이라는 **되돌리기(undo)** 기능이 있어서 중간에 잘못되면
연필로 쓴 걸 싹 지운다. 그런데 **Redis는 이 되돌리기에 낄 수 없다.** 유성펜으로 이미
써버린 점수는 롤백해도 남는다.

**실패 시나리오 — 주문 1건(점수 +600)이 들어왔을 때:**

1. 화이트보드에 먼저 순위점수 `+600`을 적었다. ✍️
2. 이어서 회계장부에 적으려는 순간 커밋이 실패했다(DB 순간 장애 등). 💥
3. 회계장부는 되돌리기로 **원래대로 복구**된다.
4. 그런데 화이트보드엔 `+600`이 **그대로 남는다.** → 장부와 순위판이 어긋남(과다 집계).

반대로 화이트보드 쓰기가 실패해서 예외를 던지면, 메시지를 **재시도**하는데 이때
일부만 반영돼 있을 수 있어 또 꼬인다.

| 상황 | 결과 |
|---|---|
| Redis 먼저 성공 → MySQL 커밋 실패 | 화이트보드만 +600 남음(되돌리기 불가) → **과다 집계** |
| Redis 실패 → 예외로 롤백 | 메시지 재시도 → Redis 부분 반영 위험 |

### 선택지

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| **A. 커밋 후 best-effort + 재구성** | MySQL 커밋 성공 후에만 `ZINCRBY`(afterCommit). 실패 시 로그 + 주기적/스케줄러 rebuild로 MySQL 기준 자가 치유 | 단순, MySQL 정합성 유지, 자가 치유 | Redis가 순간적으로 과소 집계될 수 있음 |
| **B. 트랜잭션 내 동기 반영** | `@Transactional` 안에서 `ZINCRBY` 호출 | 코드가 직관적 | 커밋 실패 시 Redis 과다 집계(롤백 불가), Redis 장애가 집계 전체를 중단시킴 |
| **C. Redis 반영 추적으로 정확히 1회** | `event_handled`처럼 "Redis에 반영했는지"를 별도 추적해 재시도에도 정확히 1회 `ZINCRBY` | 과다/과소 없이 정확 | 추적 상태·경합 관리로 복잡도↑, 랭킹 정확도 대비 과투자일 수 있음 |

### 결정

> **A — 커밋 후 best-effort + 재구성**

랭킹 ZSET은 파생 뷰고 2일이면 사라지는 데이터다. 여기에 강한 즉시 일관성을 맞추려
복잡도를 쓰는 건 과투자다. Redis는 MySQL을 진실의 원천으로 두고, 틀어지면 다시
채우면 된다.

- **B를 버리는 이유**: 커밋 실패 시 Redis가 **과다 집계**로 남고(rebuild 없이는 자가
  치유 불가), Redis 장애가 집계 파이프라인 전체를 멈춰 세운다 — 파생 캐시 때문에
  본체(장부 기록)까지 볼모로 잡히는 나쁜 거래.
- **C를 버리는 이유**: 2일이면 버려질 순위판을 위해 추적 테이블·경합 관리를 또
  만드는 건 랭킹 정확도 대비 과투자.

**A 채택 시 반드시 지킬 두 조건:**

1. **순서는 "MySQL 커밋 성공 후 Redis"** (afterCommit). 이래야 실패해도 **과소 집계**
   (덜 셈)로만 끝난다. 과소는 rebuild로 채울 수 있지만, 과다는 어디가 틀렸는지 알 수
   없다 — 과다보다 과소가 안전하다.
2. **rebuild 경로가 존재해야 한다.** best-effort로 실패한 점수를 MySQL 기준으로 다시
   채울 수단. 이는 요구사항의 콜드 스타트 Carry-Over 스케줄러와 같은 machinery다.
   (Must-Have 범위에선 rebuild **능력**만 있으면 충분하고, 주기적 자동 rebuild는
   Nice-to-Have로 미룬다.)

## 결정 2 — 멱등성 (재처리 시 ZINCRBY 중복 방지)

### 한 줄 요약

**같은 이벤트가 두 번 배달**될 수 있는데, 화이트보드엔 점수가 두 번 더해질 수 있다.

### 쉽게 풀면

Kafka는 상황에 따라 **같은 메시지를 다시 배달**한다(컨슈머 재시작, 리밸런싱, 재시도 등).
같은 택배가 두 번 오는 셈이다. 그럼 같은 주문을 두 번 세면 안 된다.

회계장부 쪽은 이미 방어가 되어 있다 — `event_handled`라는 **"처리한 사건 목록"**을
두고, 이미 있는 사건이면 그냥 무시한다(중복 안 셈).

문제는 화이트보드다. 순위점수를 올리는 `ZINCRBY`는 **"현재값에 더하기"** 라서,
두 번 부르면 그대로 **두 배**가 된다. (조회 한 번인데 화이트보드엔 +0.2가 두 번 찍히는 식)

> 핵심: 화이트보드에 점수를 더하는 일도 **반드시 "처리한 사건 목록"을 통과한 경우에만**
> 해야 한다. 이미 처리한 사건이면 화이트보드도 건드리지 말아야 한다.

**주의 — 결정 1과 얽힌다:** "처리한 사건 목록" 체크는 MySQL 트랜잭션 안에서 일어난다.
그런데 화이트보드 쓰기를 트랜잭션 **밖**(커밋 후)에 두면, "장부엔 처리했다고 적혔는데
화이트보드 반영은 실패" 하는 틈이 생긴다. 즉 **1번을 어떻게 정하냐에 따라 2번 방어법도
달라진다.**

또, 좋아요 취소(`LIKE_CANCELLED`)처럼 점수를 **깎는** 이벤트도 똑같이 두 번 깎일 위험이
있다.

### 결정

> **`event_handled` 게이트가 Redis 멱등성까지 책임진다 — 별도 추적 없음**

결정 1(A)의 흐름에 그대로 얹으면 규칙 하나로 끝난다.

```
1. @Transactional
   - event_handled 확인
     · 이미 있으면 → return (아무것도 안 함)
     · 없으면 → event_handled 기록 + product_metrics 갱신
   - 커밋
2. 커밋 성공 후 → Redis ZINCRBY   ← afterCommit
```

> **핵심 규칙: Redis 점수 반영은 "이번에 새로 처리된 이벤트"에만 건다.**
> event_handled에 이미 있어 skip한 이벤트면 Redis도 건드리지 않는다.
> (afterCommit 등록 자체를 dedup 체크를 통과한 새 이벤트 분기 안에서만 수행)

이러면 **"처리한 사건 목록" 문지기 하나가 MySQL과 Redis 양쪽의 중복을 동시에 막는다.**

**재배달 시나리오 검증:**

| 상황 | 결과 |
|---|---|
| 이미 처리된 이벤트가 또 배달 | 게이트가 skip → Redis 안 건드림. **중복 없음** |
| 커밋 후 Redis 직전 크래시 → 재배달 | 게이트가 skip(이미 기록됨) → Redis가 이 건을 놓침(**과소 집계**) |

두 번째의 과소 집계는 결정 1에서 수용하기로 한 트레이드오프이며, rebuild로 보정한다.
좋아요 취소(-0.2)의 이중 차감도 같은 게이트가 막는다.

- **별도 "Redis 반영 추적" 테이블은 만들지 않는다** (그것이 결정 1에서 버린 C안).
- 커밋~Redis 사이 크래시로 인한 과소 집계는 **의도적으로 수용**하고 rebuild로 보정.

## 결정 3 — TTL (언제/어떻게 EXPIRE)

### 한 줄 요약

순위판에 **"2일 뒤 폐기" 딱지**를 붙여야 하는데, 점수 더하기 명령은 딱지를 안 붙여준다.

### 쉽게 풀면

랭킹 키는 날짜별로 만들고(`ranking:all:{yyyyMMdd}`), **2일 뒤 자동 삭제(TTL)** 되어야
한다. 안 지우면 날짜별 순위판이 매일 쌓여 Redis 메모리를 계속 잡아먹는다.

그런데 점수를 올리는 `ZINCRBY`는 **점수만 더할 뿐, "유통기한 딱지(EXPIRE)"는 안 붙여준다.**
그래서 우리가 명시적으로 "이 키는 2일 뒤 만료" 라고 따로 걸어줘야 한다. 언제 걸지가 문제다.

### 선택지

| 전략 | 방식 | 장점 | 단점 |
|---|---|---|---|
| 매 이벤트마다 EXPIRE 갱신 | `ZINCRBY` 후 항상 `EXPIRE key 2d` | 만료가 항상 보장됨, 로직 단순 | 이벤트마다 명령 1회 추가 |
| 키 최초 생성 시 1회만 | 키가 새로 만들어질 때만 EXPIRE | 명령 최소화 | "처음"을 잡는 경합 처리 필요 |

### 결정

> **매 이벤트마다 EXPIRE 갱신 (ZINCRBY + EXPIRE를 파이프라인/Lua로 묶음)**

- **best-effort와 맞물려 자가 치유가 공짜다.** Redis 쓰기는 실패할 수 있는 게 전제
  (결정 1). "최초 1회만" 방식은 그 한 번의 EXPIRE가 실패·경합으로 누락되면 키가 영영
  안 지워진다(메모리 누수). 매번 갱신하면 이번에 실패해도 **다음 이벤트가 다시
  걸어준다** — 결정 1·2의 "틀어져도 다음에 보정" 철학과 동일.
- **단순하다.** "이 키가 방금 새로 생겼나?"를 판단할 필요가 없어 분기도 경합도 없다.
  무조건 EXPIRE를 건다.
- **비용은 사실상 없다.** ZINCRBY 옆에 EXPIRE 하나 추가. 파이프라인/Lua로 묶으면
  왕복 1회이며, Lua로 묶으면 원자적으로 처리된다.

**슬라이딩 윈도우 우려와 그 해소:** 매번 갱신하면 TTL이 "마지막 이벤트 시각 + 2일"로
밀린다("키 생성 + 2일"이 아님). 하지만 키가 `ranking:all:{yyyyMMdd}`로 날짜 고정이라,
오늘 키는 오늘 이벤트만 받고 자정 이후엔 새 키로 넘어간다. 오늘 키의 마지막 이벤트는
늦어야 23:59 → 모레 23:59까지 유지되어, 요구사항 **"이전 날짜 랭킹도 정상 조회"**를
오히려 확실히 만족한다. 활동 없는 옛 키는 자연 만료된다.

## 가중치 산정

### 한 줄 요약

세 신호(조회·좋아요·주문)의 **스케일을 맞춰** 한 판에서 겨루게 한다. 특히 주문 금액은
**log로 정규화**해 한 건이 전부를 부수지 않게 한다.

### 문제 — 자릿수가 다르다

요구사항 예시(점수 = Weight × Score)를 그대로 쓰면:

```
조회   : 0.1 × 1
좋아요 : 0.2 × 1
주문   : 0.6 × (price × amount)
```

주문 항만 자릿수가 다르다. 15만원 1개면 `0.6 × 150000 = 90,000점`, 조회 한 번은 `0.1점`.
**주문 1건 = 조회 90만 번**과 맞먹어 조회·좋아요가 사실상 노이즈가 된다.

| | 조회 | 좋아요 | 주문 | 원시 점수 |
|---|---|---|---|---|
| 상품 A | 1000 | 100 | 0 | 1000×0.1 + 100×0.2 = **120** |
| 상품 B | 1 | 0 | 20만원 1개 | 0.6×200000 = **120,000** |

딱 한 명이 산 B가 조회 1000·좋아요 100의 A를 **1000배**로 누른다. "진짜 인기상품"과
거리가 멀다(롱테일 문제).

### 결정 — 주문 금액에 log 정규화

```
조회   score += 0.1
좋아요 score += 0.2   (취소 시 -0.2)
주문   score += 0.6 × log10(1 + price × amount)
```

가중치 0.1 / 0.2 / 0.6은 요구사항 예시값을 그대로 쓴다(상대적 중요도). 주문 금액만
log10으로 정규화한다.

### 왜 log인가

log는 **곱셈으로 벌어지는 차이를 덧셈으로 눌러주는** 자다. 값이 10배 될 때마다 +1.

| 주문 금액 | 원시값 | log10(1+금액) |
|---|---|---|
| 1,000원 | 1,000 | ≈ 3.0 |
| 10,000원 | 10,000 | ≈ 4.0 |
| 100,000원 | 100,000 | ≈ 5.0 |
| 1,000,000원 | 1,000,000 | ≈ 6.0 |
| 10,000,000원 | 10,000,000 | ≈ 7.0 |

1천원~1천만원의 **10,000배** 범위가 `3.0~7.0`(약 2.3배)로 눌린다. 비쌀수록 유리하되
**점점 완만하게**(diminishing returns) 올라 한 건이 전부를 부수지 않는다.

- **가중치만 낮추면?** 여전히 선형이라 지배 구도가 안 바뀐다(전체만 작아짐).
- **상한선(cap)?** 특정 금액에서 뚝 끊기는 절벽이 생긴다.
- **log?** 절벽 없이 부드럽게 완만해진다 → 정석.

`log(1 + 금액)`으로 감싸는 건 `log(0) = -∞` 폭주와 음수를 막아 0원이면 0점이 되게
하기 위함이다.

### 곁다리

- **소수점 vs 정수**: log 점수는 `3.18` 같은 double이다. 우리는 **순서만** 필요하므로
  부동소수점 미세 오차가 순위를 뒤집지 않는다 → 정수 스케일링 없이 double 그대로 쓴다.
- **가중치 위치**: 0.1/0.2/0.6을 상수로 시작하되 `application.yml`로 뺄 수 있게 구조만
  잡아두면 Nice-to-Have "실시간 Weight 조절"로 자연스럽게 이어진다.

- 가중치를 어디에 둘지 (상수 vs 설정 vs Redis) — 실시간 Weight 조절과 연결
