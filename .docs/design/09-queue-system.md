# 09. 대기열 시스템

블랙 프라이데이처럼 순간적으로 대규모 트래픽이 몰릴 때, 주문 API 앞단에 대기열을 두어
시스템을 보호하면서 유저에게 공정한 대기 경험을 제공한다.

## 전체 흐름

```
[유저] POST /queue/enter
     → Redis Sorted Set에 줄 세움 (INCR 카운터로 순번 부여)

[유저] GET /queue/position (polling) 또는 GET /queue/stream (SSE)
     → WAITING + 순번  →  ...  →  READY + 입장 토큰

[스케줄러] 100ms마다 실행
     → ZPOPMIN으로 앞에서 10명 꺼냄
     → 입장 토큰 발급 (Redis SET, TTL 5분, Jitter visibleAt 부여)

[유저] POST /orders (Header: X-Entry-Token)
     → 토큰 검증 → 주문 처리 → 성공 시 토큰 삭제
```

---

# 왜 대기열인가 — 세 가지 전략 비교

**아무것도 없을 때** — 모든 요청이 그대로 주문 API에 진입. DB 커넥션 풀 고갈 → 타임아웃 → 500/503. 먼저 클릭했어도 커넥션 경쟁에서 밀리면 실패한다. 서버가 스스로 무너지는 최악의 형태.

**Rate Limiting** — 초당 허용 요청 수를 정해 초과분을 429로 즉시 거부. 시스템 부하는 확실히 제한되지만, 거부당한 유저는 재시도하거나 이탈해 **주문 기회 자체를 잃는다**. 먼저 클릭했어도 429를 받으면 끝 — 여전히 불공정하다.

**대기열** — 거부하지 않고 줄을 세운다. 시스템이 감당할 수 있는 속도로만 통과시킨다. 진입 순서가 보장되고, 순번·예상 대기 시간을 보여주면 유저 이탈이 감소한다. 대신 구현 복잡도가 높다.

|  | 아무것도 없음 | Rate Limiting | 대기열 |
|---|---|---|---|
| 초과 요청 처리 | 그대로 받다가 터짐 | 즉시 거부 (429) | 줄 세움 |
| 에러 종류 | 500 / 503 | 429 | 없음 (대기) |
| 공정성 | 낮음 (커넥션 운) | 낮음 (속도 운) | 높음 (순서 보장) |
| 유저 경험 | 에러/성공 양극단 | 거부 → 이탈 | 기다리지만 예측 가능 |
| 구현 복잡도 | 낮음 | 낮음 | 높음 |

> Rate Limiting은 "초과분을 잘라낸다", 대기열은 "초과분을 나중에 처리한다".
> 주문처럼 **기회를 보존해야 하는 상황**에서는 대기열이 적합하다.
> 단, 둘은 양자택일이 아니다 — 대기열에도 상한을 두고 초과분은 429로 거부하므로,
> 실제로는 "대기열 뒤에 Rate Limiting을 한 겹 더 둔" 조합 구조가 된다.

# Step 1 — Redis 기반 대기열

## 설계 결정

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | Score 방식 | Redis `INCR` 카운터 | 원자적 보장, 서버 시계 편차 무관 |
| 2 | Key | 단일 `queue:waiting` | 과제 범위상 상품/이벤트별 분리 불필요 |
| 3 | Member | userId | Sorted Set unique 특성으로 중복 자동 방지 |
| 4 | 중복 진입 | 기존 순번 유지 (`ZADD NX`) | 새로고침/재시도에 안전 |
| 5 | 대기열 상한 | 있음 (초과 시 429) | Redis 메모리 보호 |

### 왜 Score를 timestamp가 아닌 카운터로?

`System.currentTimeMillis()`는 ms 정밀도라 동시 진입 시 겹칠 수 있다. 서버가 여러 대면 시계 편차로 순서가 뒤집힐 수도 있다. `INCR`은 Redis가 원자적으로 처리하므로 절대 겹치지 않고, 서버 시계에도 무관하다.

### 왜 중복 진입에 "기존 순번 유지" 정책인가?

이미 대기 중인 유저의 재요청은 무시하고 기존 순번을 그대로 반환한다(`ZADD NX`). 새로고침·네트워크 재시도에도 안전하다. 티켓팅 서비스가 쓰는 "새로고침 시 밀림" 정책은 극단적 트래픽 억제엔 유리하지만 유저를 벌하는 방식 — 이커머스 주문에서는 트래픽 억제보다 유저 신뢰 유지가 우선이라 채택하지 않았다.

## 핵심 구현 — 원자적 진입 (Lua Script)

진입에는 네 가지가 필요하다: 중복 확인 → 상한 확인 → 순번 발급 → 줄 세우기. 이걸 별도 명령으로 날리면 명령 사이 다른 요청이 끼어들어 상한이 뚫리거나 순번이 중복될 수 있다. 하나의 Lua로 묶어 원자적으로 처리한다.

```lua
if redis.call('ZSCORE', KEYS[1], ARGV[1]) then
  return redis.call('ZRANK', KEYS[1], ARGV[1]) + 1
end
if redis.call('ZCARD', KEYS[1]) >= tonumber(ARGV[2]) then
  return -1
end
local score = redis.call('INCR', KEYS[2])
redis.call('ZADD', KEYS[1], score, ARGV[1])
return redis.call('ZRANK', KEYS[1], ARGV[1]) + 1
```

이미 있으면 기존 순번 반환, 상한 초과면 `-1` 반환(Facade에서 429로 변환), 그 외엔 새 순번을 발급한다.

## API

| Method | Path | 응답 상태 |
|---|---|---|
| POST | `/api/v1/queue/enter` | 200 / 400 / 429 |
| GET | `/api/v1/queue/position?userId=` | 200 / 400 |
| GET | `/api/v1/queue/size` | 200 |

응답은 상태가 달라도 필드 구성이 같고 `status`(WAITING / READY / NOT_IN_QUEUE)로 구분한다. 프론트가 상태별로 파싱 로직을 분기하지 않아도 되도록 하기 위함.

# Step 2 — 입장 토큰 & 스케줄러

## 설계 결정

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | 스케줄러 주기 / 배치 | 100ms / 10명 | 아래 산정 근거 |
| 2 | 대기열에서 꺼내기 | `ZPOPMIN N` | "앞에서 N명 조회+삭제"가 원자적 명령 하나 |
| 3 | 토큰 TTL | 5분 | 주문서 확인+결제 수단 선택에 충분, 미사용 토큰 슬롯 점유 최소화 |
| 4 | 토큰 저장 | `queue:token:{userId}` = 토큰값 | userId 키 하나로 소유자 확인·READY 분기·만료 모두 해결 |
| 5 | 토큰 검증 위치 | OrderFacade 진입부 | 구조 단순, 통합 테스트 용이. 인터셉터는 대상 API가 늘어날 때 재검토 |
| 6 | 토큰 삭제 시점 | 주문 성공 시에만 | 실패(재고 부족·결제 실패) 시 TTL 내 재시도 가능 |
| 7 | 만료 유저 | 처음부터 재진입 | 대기열·토큰 모두 없는 상태 → 다시 줄 서기 |
| 8 | 스케줄러 다중화 | 단일 인스턴스 가정 | 다중화 시 ShedLock 등 분산 락 필요 — 과제 범위 밖 |

### 배치 크기 산정 근거

```
DB 커넥션 풀:           40개 (HikariCP maximum-pool-size)
주문 API 몫:            50% → 20개 (상품 조회 등 다른 API와 풀 공유)
주문 평균 처리 시간 가정: 200ms (실측 전 보수적 가정)

초당 입장 가능 = 20 × (1000ms / 200ms) = 초당 100명
스케줄러 100ms 주기 → 배치 크기 = 100 / 10 = 10명
```

1초에 100명을 한 번에 몰아넣지 않고 100ms마다 10명씩 쪼갠 이유는, 같은 총량이라도 시간축으로 분산돼 주문 API 스파이크(Thundering Herd)가 완화되기 때문이다. 또 토큰 발급 ≠ 즉시 주문이므로 실제 DB 유입은 이보다 완만하게 퍼진다 — 위 수치는 "최악의 경우(전원 즉시 주문)"에도 풀이 버티는 보수적 기준. 실측 값이 쌓이면 보정한다.

### 왜 userId를 토큰 key로?

`queue:token:{userId}` = UUID (TTL 300초). userId를 키로 삼으면 세 가지가 별도 장치 없이 해결된다:

1. **소유자 확인** — 검증 시 "요청 유저의 키"를 조회해 헤더 토큰과 비교하므로 남의 토큰으로는 통과 불가
2. **만료 처리** — Redis TTL이 자동 삭제. 만료 검사 코드가 필요 없다 ("키 없음" = "미발급 또는 만료")
3. **READY 조회** — 순번 조회 시 이 키 하나만 확인하면 발급 여부를 판정할 수 있다

### getPosition 상태 분기 (Step 2에서 변경 필수)

스케줄러가 `ZPOPMIN`으로 꺼낸 유저는 ZRANK가 null이 되므로, 토큰 확인 없이는 `NOT_IN_QUEUE`로 오판된다. 반드시 토큰을 먼저 확인해야 한다.

```
1. queue:token:{userId} 존재? → READY + 토큰
2. ZRANK 존재?              → WAITING + 순번
3. 둘 다 없음               → NOT_IN_QUEUE
```

### 트레이드오프

- **ZPOPMIN과 토큰 SET 사이 장애** — 꺼낸 뒤 토큰 발급 전에 서버가 죽으면 해당 유저는 대기열·토큰 모두 없는 상태가 된다. 두 명령을 Lua로 묶어 원자화하는 대신, "유저가 재진입하면 복구된다"로 허용했다. 발생 확률 대비 구현 복잡도를 낮추는 선택.
- **토큰 동시 사용 가능성** — 성공 시에만 삭제하는 정책상 같은 토큰의 동시 요청이 이론상 가능하다. `GETDEL`로 검증+삭제를 원자화하면 막을 수 있지만, 이 경우 주문 실패(재고 부족·결제 실패) 시 재시도가 불가능해진다. 재시도 가능성 쪽을 택했고, 재고 차감 로직이 최종 방어선이 된다.

### 주문 흐름의 정책이 코드에 그대로 드러난다

```java
entryTokenValidator.validate(userId, entryToken);   // ① 검증 (실패 → 403)
OrderInfo info = createOrder(...);                  // ② 주문 (여기서 예외 → 토큰 유지)
entryTokenValidator.consume(userId);                // ③ 성공했을 때만 삭제
```

403(FORBIDDEN)을 쓴 이유: 로그인은 이미 된 유저이고, 부족한 것은 인증이 아니라 "입장 권한"이다. 401은 어울리지 않는다.

### 설정

| 키 | 값 | 의미 |
|---|---|---|
| `queue.max-size` | 100000 | 대기열 상한 (초과 시 429) |
| `queue.scheduler.enabled` | true (test는 false) | 스케줄러 on/off |
| `queue.scheduler.interval-ms` | 100 | 실행 주기 |
| `queue.scheduler.batch-size` | 10 | 회당 입장 인원 |
| `queue.token.ttl-seconds` | 300 | 토큰 TTL 5분 |
| `queue.entry-token.required` | true | false 시 검증 우회 (Redis 장애 kill switch) |

> 테스트 환경 주의: 컨텍스트 캐시에 남은 다른 컨텍스트의 스케줄러가 공유 Redis 대기열을 비워 순번 검증을 오염시키는 문제가 있어, test 프로파일에서는 스케줄러를 끄고 `admitNextBatch()`를 수동 호출로 검증한다.

# Step 3 — 실시간 순번 조회 (예상 대기 시간)

## 설계 결정

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | 처리량 산정 | 정적 — 설정값 기반 (초당 100명) | 스케줄러 처리량은 우리가 통제하는 값, 변동 요인 적음 |
| 2 | 표시 방식 | 초 단위 정수, 올림 | 분 환산은 프론트 몫 |
| 3 | 다음 배치 예정자 | position ≤ batch-size → 0초 | "곧 입장" 표시 |
| 4 | pollAfter 구간 기준 | 예상 대기 시간 기준 | 임박할수록 자주 조회, 배치 설정이 바뀌어도 자동 반영 |
| 5 | READY 응답 | expiresAt 포함 (Redis TTL 조회) | "5분 안에 주문하세요" 카운트다운 제공 |

### 왜 정적 처리량 산정인가?

스케줄러 처리량은 우리가 통제하는 값이라 변동 요인이 적다. "최근 N분간 실제 통과 인원"을 측정해 동적으로 산정하는 방식은 정확도는 높지만 구현·검증 복잡도가 크고, 이번 과제에서 얻는 이득이 작다. 다만 스케줄러가 멈추면 예상 시간이 실제와 어긋나는 한계가 있어, 운영에서 처리량이 설정값과 크게 달라지면 실측 기반으로 전환을 검토한다.

### 계산

```
초당 처리량 = batch-size × (1000 / interval-ms) = 10 × 10 = 100명/초
estimatedWaitTime(초) = position ≤ batch-size 이면 0
                        아니면 ceil(position / 100)
예: position 342 → ceil(3.42) = 4초
```

### pollAfter로 Polling 부하 완화

대기 10만 명이 2초마다 polling하면 초당 5만 요청. Redis의 ZRANK(O(log N))보다 톰캣 워커 스레드(200개)가 먼저 병목이 된다. 응답에 다음 조회 권장 간격을 담아 총량을 줄인다.

| 예상 대기 시간 | pollAfter |
|---|---|
| 60초 이상 | 10초 |
| 10~60초 | 5초 |
| 10초 미만 | 2초 |
| READY / NOT_IN_QUEUE | null |

서버가 강제할 수는 없는 클라이언트 가이드라는 한계가 있다. 커스텀 클라이언트나 봇은 무시할 수 있다.

# Step 4 — Thundering Herd 완화 (Jitter)

## 배경

스케줄러 배치는 이미 시간축에 분산돼 있다(100ms마다 10명). 그럼에도 같은 100ms 틱에 발급된 10명은 사실상 동시에 주문 API를 두드린다. Jitter는 그 안에서도 각 유저의 "노출 가능 시각"을 랜덤 지연으로 흩뿌려 스파이크를 한 번 더 완화한다.

## 설계 결정

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | 위치 | 토큰 발급 후 노출/검증까지의 시각 | 실제 스파이크(주문 API)를 가장 직접 완화 |
| 2 | 범위 | `[0, 500ms]` | 배치 간격 100ms의 5배 |
| 3 | 강제 방식 | **서버가 검증에서도 차단** | 클라이언트 Jitter는 커스텀 클라이언트로 우회 가능 |
| 4 | 저장 방식 | 기존 토큰 value에 `visibleAtMillis\|token` 인코딩 | 단일 GET/SET 유지, 추가 키 없음 |
| 5 | 대기 중 응답 | `WAITING` 재사용 + `position=0` | 클라이언트 로직 최소 변경, WAITING→READY 흐름 유지 |

### 위치 선택 — 왜 "토큰 발급 후 노출"인가?

Jitter를 넣을 수 있는 위치는 세 가지가 있었다.

- **A. 스케줄러 배치 발급 시점** — 이미 100ms/10명으로 쪼갠 뒤라 추가 효과가 작음
- **B. 토큰 발급 후 → 유저 노출까지** — 실제 스파이크(주문 API)를 가장 직접 완화 ✅
- **C. Polling 재조회 주기(`pollAfter`)에 Jitter** — Polling 부하 완화 목적이지 스파이크 완화가 아님

B가 목적에 가장 부합해서 선택했다.

### 강제 방식 — 왜 검증도 서버가 막나?

클라이언트 쪽에서 랜덤 지연을 넣는 방식은 서버 구현이 단순하지만, 커스텀 클라이언트/봇은 이걸 무시하고 즉시 주문을 던질 수 있다. 서버가 `visibleAt` 이전 검증 시도를 FORBIDDEN으로 막으면 시간축 분산이 실제로 강제된다. 정상 유저는 어차피 서버 READY 응답 전엔 토큰을 알 수 없어서 실질적 이 케이스는 발생하지 않지만, 방어선 역할을 한다.

### 범위 — 왜 500ms인가?

배치 간격(100ms)의 5배. 유저 체감 지연은 무시할 수준(0.5초)이면서 배치 내 10명이 500ms에 걸쳐 흩어진다. 너무 작으면(예: 100ms) 효과가 미미하고, 너무 크면(예: 5초) 유저가 "왜 안 넘어가?" 느낀다. 최적값은 실측 후 조정 대상 — 지금은 이론값.

### 저장 방식 — 왜 별도 키가 아니라 인코딩인가?

`queue:token:visible:{userId}` 같은 별도 키를 두면 읽을 때마다 GET 2회가 필요하다. 기존 토큰 value에 `visibleAtMillis|token` 형태로 인코딩하면 명령 수는 그대로 유지된다. 파싱은 `indexOf('|')` 한 줄 — 복잡도 비용이 낮다.

## 동작 흐름

```
[스케줄러] ZPOPMIN → EntryTokenModel.issue(userId, 500)
     → visibleAt = now + random(0, 500ms)
     → queue:token:{userId} = "1728...|abc-uuid"

[유저] GET /queue/position
     → 토큰 있음 && visibleAt 지남   → READY + 토큰
     → 토큰 있음 && visibleAt 이전   → WAITING (position=0, estimatedWaitTime=남은 초)
     → 토큰 없음                     → 기존 ZRANK 로직

[유저] POST /orders (visibleAt 이전)
     → validate → FORBIDDEN (방어선, 정상 흐름에선 발생 안 함)
```

`queue.jitter.max-ms`는 프로덕션 500, test 프로파일 기본 0. `0`이면 즉시 노출되어 기존 통합/E2E 테스트를 그대로 통과시킬 수 있다.

## 실측 결과

k6 스크립트(`k6/queue-jitter-test.js`)로 100 유저 동시 진입, `PRODUCT_ID=1` 재고 10만 조건에서 측정.

| 지표 | Before (jitter=0) | After (jitter=500) | 개선 |
|---|---|---|---|
| order_latency avg | 4.94s | 1.99s | −60% |
| order_latency p50 | 5.25s | 2.20s | −58% |
| order_latency p95 | 6.10s | 2.42s | −60% |
| order_latency max | 7.08s | 2.63s | −63% |
| total_latency p95 | 9.52s | 5.01s | −47% |
| 성공률 | 100/100 | 100/100 | — |

`total_latency`는 "대기열 진입 → 주문 완료"까지의 총 시간이고, `order_latency`는 그중 주문 API 자체의 응답 시간이다.

### 알게 된 것 1 — 성공률만 봐서는 Jitter 효과가 안 보인다

두 케이스 모두 성공률 100/100. "그럼 Jitter 없어도 되는 거 아냐?"로 오독하기 쉽지만, **유저가 실제로 체감하는 건 성공/실패가 아니라 지연 분포**다. Jitter가 없을 때 어떤 유저는 1.15s만에 끝나고 어떤 유저는 7.08s를 기다렸다. p50과 max가 6배 차이나는 상태는 "성공은 했지만 누군가는 대기창을 오래 노려봐야 하는" 서비스다. Jitter를 켜면 이 편차가 좁혀진다.

이건 실서비스의 SLO 관점에서도 중요하다. SLO는 보통 p95, p99 같은 tail latency로 정의되고 알럿도 tail 기준으로 울린다. avg가 아니라 **max/p95를 얼마나 낮추느냐가 실제 사용자 경험과 알럿 노이즈를 결정**한다.

### 알게 된 것 2 — Jitter가 유저 개인을 늦추는데 총 시간(total_latency)은 오히려 줄었다

Jitter의 정의만 보면 반직관적이다. "각 유저를 0~500ms 랜덤 지연시킨다"고 하면 유저 입장에서는 손해가 있어야 정상인데, `total_latency` p95가 9.52s → 5.01s로 4.5초나 짧아졌다.

이유는 **주문 API 자체가 빨라졌기 때문**이다. Jitter가 없을 때는 같은 배치 10명이 거의 동시에 주문 API를 두드려 커넥션·락 경합이 발생하고, 이게 뒤 배치 처리까지 지연시킨다. Jitter가 들어가면 경합이 줄어들어 배치 하나가 빨리 소화되고, 다음 배치 유저의 대기 시간도 함께 짧아진다. "각자 500ms 참는 대가로 전체 처리가 빨라지고, 결과적으로 개인 총 대기 시간도 짧아진다"가 실측으로 확인된 것.

### 알게 된 것 3 — max값이 배치 간격 근처로 붙었다

After에서 order_latency max=2.63s. 배치 크기 10 × 주문 처리 200ms 가정 = 2s가 이론적 최소 하한이고, 실측이 여기 근처에 붙었다. Jitter가 "배치 내 경합"을 거의 제거해 지연이 순수하게 "배치 순번 대기"로만 결정되는 상태에 가까워진 셈. 반면 Jitter 없을 때의 max=7.08s는 배치 경합이 지연에 얼마나 크게 기여하는지 보여준다.

### 고민해볼 지점

- **500ms가 정말 최적인가** — 200ms, 1s 등 다른 값으로 곡선을 그려봐야 안다. 이 실측이 보여주는 건 "500ms에서 확실히 효과가 있다"이지 "500ms가 최적이다"가 아니다.
- **부하 규모에 따른 곡선 모양** — 100 유저는 배치(10명) 몇 번이면 끝나는 소규모다. 초당 수천 요청 규모에서는 커넥션 풀이 지속적으로 포화 상태에 있어 곡선이 다르게 그려질 가능성이 있다. Jitter 효과가 더 커질 수도, 반대로 다른 병목(예: DB 락)이 지배적이 되어 잘 안 보일 수도 있다.
- **유저 체감 임계값** — 500ms는 서비스에 따라 "즉시"로 느끼는 값이지만, 결제처럼 긴장한 상태에서는 다를 수 있다. 실측 optimum과 유저가 참을 수 있는 상한이 겹치는 지점을 찾는 게 이상적.

## 한계

- **최대 지연이 이론값** — 배치 간격의 5배라는 근거는 합리적이지만 실측 최적값은 아니다. 위 결과는 500ms가 100 유저 규모에서 효과가 있다는 정도만 보여준다. 유저 체감 vs 스파이크 완화 곡선을 그려 최적 지점을 찾는 것은 후속 작업.
- **부하 규모 한계** — 100 유저 스케일이라 배치(10명) 여러 번으로 처리가 끝나고 커넥션 풀(40)이 여유롭다. 초당 수천 요청 규모에서 절대 효과가 어떻게 바뀌는지는 별도 실측 필요.

# Step 5 — SSE 기반 순번 Push (Polling 병행)

## 배경

Polling으로도 대기 경험은 충분히 제공된다. 그럼에도 SSE를 붙인 이유는 "서버가 push하는" 방식이 실서비스에서 어떤 트레이드오프를 갖는지 학습 목적이다. **대체가 아니라 병행** — 기존 `/queue/position`은 그대로 두고 `/queue/stream`을 추가한다.

## 설계 결정

| # | 항목 | 결정 | 근거 |
|---|---|---|---|
| 1 | 대체 vs 병행 | **병행** | Polling은 무상태·수평 확장 유리, SSE는 학습·데모용 |
| 2 | 규모 | 데모 (단일 인스턴스, 로컬 Map) | 다중 인스턴스는 Pub/Sub 인프라 필요 — 범위 밖 |
| 3 | 트리거 | **스케줄러 push** | 배치 처리 직후가 상태 변화가 실제로 있는 시점 |
| 4 | broadcast 대상 | 등록된 emitter 전원 | 데모 규모(수십~수백)면 감당 가능 |
| 5 | Jitter와 상호작용 | broadcast도 `getPosition()` 재사용 | visibleAt 이전 유저는 SSE로도 `position` 이벤트만 받음 |

### 트리거 선택 — 왜 "스케줄러 push"인가?

SSE 이벤트를 언제 발사할지 세 가지 옵션이 있었다.

- **A. 주기적 push (예: 1초마다 서버가 순번 계산해서 전송)** — Polling과 다를 게 없어서 SSE의 장점이 사라짐
- **B. 스케줄러 push (배치 처리 직후 대기자 전원에게 push)** — 상태가 실제로 변한 시점, SSE 이점을 살림 ✅
- **C. Redis Pub/Sub으로 변화 이벤트 구독** — 다중 인스턴스에 대비되지만 인프라 추가 필요, 데모 규모엔 과함

B가 데모 규모 + 학습 목적에 가장 잘 맞아서 선택했다.

### broadcast 대상 — 왜 전원인가?

배치에서 나간 10명은 상태가 확실히 바뀌지만(READY), 남은 대기자들도 순번이 앞당겨졌다. "변화가 있는 유저만" 골라내려면 이전 순번을 저장하고 비교해야 하는데, 데모 규모(수십~수백)에서는 그 최적화가 얻는 이득보다 복잡도 비용이 크다. 대규모로 가면 재검토 대상.

### Jitter와의 일관성

broadcast 시 `getPosition()`을 그대로 재사용한다. 즉 스케줄러가 배치 처리 직후 push해도, visibleAt이 미래인 유저에게는 `ready`가 아니라 `position` 이벤트가 간다. 폴링과 SSE가 같은 응답 로직을 공유하므로 두 채널이 서로 다른 답을 주지 않는다.

## 이벤트 스펙

```
event: position       ← WAITING (스트림 유지)
data: {"status":"WAITING","position":342,"estimatedWaitTime":4,...}

event: ready          ← READY (전송 후 emitter.complete)
data: {"status":"READY","token":"abc123...","expiresAt":"..."}

event: error          ← NOT_IN_QUEUE (전송 후 complete)
data: {"message":"대기열에 없는 유저입니다."}
```

## 연결 관리

- Timeout **30분** (`new SseEmitter(1_800_000L)`)
- `onCompletion` / `onTimeout` / `onError` 3종 콜백에서 Map 정리
- 같은 유저가 재구독하면 이전 emitter를 `complete()` 처리 후 새 것으로 대체 (좀비 커넥션 방지)

## 한계

- **다중 인스턴스 불가** — Map이 서버 로컬. 유저가 서버 A에 붙었는데 스케줄러가 서버 B에서 돌면 push 도달 안 함. 실서비스는 Redis Pub/Sub이나 Kafka 브로드캐스트가 필요하다.
- **커넥션 유지 비용** — 톰캣 워커 200개 기준 SSE 커넥션 하나가 스레드를 잡는다 → 200명이 한계. Reactive/WebFlux로 가면 수만 명 가능하지만 프로젝트 스택 전체 변경이라 범위 밖.
- **broadcast 부하** — 매 배치(100ms)마다 등록 유저 전원에 대해 `getPosition()` → Redis 왕복 N회. 대규모에서는 "변화 있는 유저만" 최적화 필요.

## Polling vs SSE — 다시 정리

| | Polling (기존) | SSE (신규) |
|---|---|---|
| 서버 상태 | 무상태 | Map 유지 (커넥션 상태) |
| 확장성 | 수평 확장 쉬움 | 서버당 커넥션 상한, 다중화 시 Pub/Sub 필요 |
| 실시간성 | 2~10초 지연 | 즉시 (배치 push) |
| 프론트 구현 | 단순 (setInterval) | EventSource API |
| 이번 선택 | 프로덕션 기본 | 학습·데모, 병행 옵션 |

프로덕션 기본은 여전히 Polling이다. SSE는 "이 대기열이 실시간이면 어떻게 만들었을까"를 실험해본 부산물에 가깝다.
