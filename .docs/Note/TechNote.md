# 요청을 버리지 않고 미뤄두는 법

요구사항은 한 줄이다.

> 블랙 프라이데이급 트래픽에도 시스템을 보호하면서, 유저에게 공정한 대기 경험을 제공할 것.

주문 API 앞단에 Redis 기반 대기열을 세우는 과제였다. 막상 구현을 시작하니 이 한 줄이 다섯 개의 질문으로 쪼개졌고, 질문마다 선택지가 있었고, 선택지마다 버려야 하는 것이 있었다.

이 글은 그 다섯 개의 질문에 어떻게 답했는지의 기록이다.

## TL;DR

주문은 유저에게 "기회"라서, 거부(429) 대신 줄을 세웠다. 순번은 Redis `INCR`로 겹치지 않게 매기고, 입장 속도는 커넥션 풀에서 역산해 초당 100명 — 몰아넣지 않고 100ms마다 10명씩 쪼갠다. 입장 토큰은 실패한 유저가 재시도할 수 있도록 주문 성공 시에만 지우고, 기다리는 유저에게는 예상 시간과 조회 주기(`pollAfter`)를 준다. **거부 대신 대기를 택했다면, 설계의 절반은 "기다리는 경험"이어야 한다.**

## 다섯 개의 질문

1. 넘치는 요청 — **거부할 것인가, 세워둘 것인가**
2. 공정한 줄은 **어떻게 만드는가**
3. **몇 명씩** 들여보낼 것인가
4. 입장권의 수명은 **몇 분인가**
5. 기다리는 유저에게 **무엇을 보여줄 것인가**

완성된 시스템의 전체 그림을 먼저 두고 시작한다. 질문 1~2가 왼쪽(줄 세우기), 3~4가 가운데(들여보내기), 5가 아래(기다리는 경험)에 해당한다.

```
[유저] POST /queue/enter
     → Redis Sorted Set에 줄 세움 (INCR 카운터로 순번 부여)

[유저] GET /queue/position (polling)
     → WAITING + 순번 + 예상 대기 시간  →  ...  →  READY + 입장 토큰

[스케줄러] 100ms마다 실행
     → ZPOPMIN으로 앞에서 10명 꺼냄
     → 입장 토큰 발급 (Redis SET, TTL 5분)

[유저] POST /orders (Header: X-Entry-Token)
     → 토큰 검증 → 주문 처리 → 성공 시 토큰 삭제
```

> **[그림 1]** 대기열 전체 흐름 — 진입 → 폴링 → 스케줄러 입장 처리 → 토큰 검증 → 주문

## 질문 1. 거부할 것인가, 세워둘 것인가

자리 20개인 식당에 손님 100명이 들이닥쳤다. 문을 그냥 열어두면 주방이 마비되고, 이미 앉은 손님의 음식도 안 나온다. 그러니 "다 받는다"는 애초에 선택지가 아니다. 남는 건 둘이다. 돌려보내거나, 줄을 세우거나.

**선택지 A — Rate Limiting.** 초당 허용량을 정하고 초과분은 429로 즉시 거부한다. 시스템 부하가 확실하게 제한되고 구현도 단순하다. 문제는 거부당한 유저다. 먼저 클릭했어도 429를 받으면 끝 — 재시도하거나 이탈하면서 **주문 기회 자체를 잃는다**. 늦게 클릭한 유저가 운 좋게 통과할 수 있으니, 시스템은 지켜지는데 공정함이 무너진다.

**선택지 B — 대기열.** 거부하지 않고 줄을 세운 뒤, 시스템이 감당 가능한 속도로만 통과시킨다. 진입 순서가 보장되고, 순번과 예상 시간을 보여주면 이탈도 줄어든다. 대가는 구현 복잡도다.

|  | 아무것도 없음 | Rate Limiting | 대기열 |
|---|---|---|---|
| 초과 요청 처리 | 그대로 받다가 터짐 | 즉시 거부 (429) | 줄 세움 |
| 공정성 | 낮음 (커넥션 운) | 낮음 (속도 운) | 높음 (순서 보장) |
| 유저 경험 | 에러/성공 양극단 | 거부 → 이탈 | 기다리지만 예측 가능 |
| 구현 복잡도 | 낮음 | 낮음 | 높음 |

> **[그림 2]** 세 가지 자세 비교 — 문 열어두기(붕괴) / 돌려보내기(기회 상실) / 번호표(순서 보장)

갈림길의 기준은 결국 이것이었다. **그 요청은 유저에게 무엇인가?** 봇 트래픽이나 단순 조회라면 잘라내도 된다. 하지만 주문은 유저에게 "기회"이고, 기회는 운이 아니라 순서로 배분되어야 한다. 그래서 대기열이다.

다만 만들고 나서 알게 된 게 하나 있다. 대기열도 무한히 받을 수는 없다 — Redis 메모리는 유한하니 상한(10만 명)을 두고, 초과분은 429로 거부한다. 어라, 이건 Rate Limiting이다. 즉 둘은 양자택일이 아니었다. **기회를 보존하는 층(대기열) 위에 시스템을 보호하는 층(상한 429)을 겹쳐 쌓는 것**이 실제 답이었다.

## 질문 2. 공정한 줄은 어떻게 만드는가

Redis Sorted Set에 userId를 member로, 순번을 score로 넣으면 줄이 된다. 간단해 보이지만 "공정한" 줄이 되려면 세 가지가 필요했다. 번호가 절대 겹치지 않을 것, 새로고침해도 자리가 유지될 것, 끼어들기가 불가능할 것.

### 번호가 겹치지 않을 것 — timestamp를 버리고 카운터로

score의 첫 후보는 자연스럽게 `System.currentTimeMillis()`였다. 진입 시각이 곧 순서니까. 그런데 구멍이 두 개다.

- **ms 정밀도 충돌** — 대규모 동시 진입에선 같은 밀리초에 여러 명이 들어와 score가 겹친다.
- **서버 시계 편차** — 서버가 여러 대면 시계가 미묘하게 달라, A 서버로 먼저 온 유저가 B 서버로 늦게 온 유저보다 뒤 순번을 받을 수 있다.

Redis `INCR` 카운터는 둘 다 없다. Redis가 단일 지점에서 원자적으로 증가시키니 절대 겹치지 않고, 어느 서버를 거쳤는지도 무관하다. "순서"의 기준을 각 서버의 시계가 아니라 **Redis 도착 순서 하나로 통일**한 것이다.

### 자리가 유지될 것 — 새로고침한 유저를 벌하지 않는다

대기 중 불안해서 새로고침을 누르는 건 자연스러운 행동이다. 그런데 티켓팅 서비스의 대기열 화면을 떠올려보면, 하단에 이런 안내가 붙어 있곤 하다 — **"새로고침하시면 대기 순번이 뒤로 밀릴 수 있습니다."**

> **[그림 3]** 티켓팅 대기열 화면 — 새로고침 시 순번이 밀린다는 안내

재접속을 새 진입으로 취급해 줄 맨 뒤로 보내는 정책이다. 새로고침 연타 자체를 억제해 극단적인 트래픽을 줄이는 효과는 있지만, 불안해서 누른 유저를 벌하는 방식이기도 하다. 이커머스 주문에서는 트래픽 억제보다 유저 신뢰가 우선이라 판단해 반대를 택했다. 재요청은 무시하고 기존 순번을 그대로 돌려준다(`ZADD NX`). 네트워크 재시도에 안전해지는 건 덤.

### 끼어들 수 없을 것 — 네 단계를 Lua 하나로

진입 한 번에 필요한 일은 넷이다: 중복 확인 → 상한 확인 → 순번 발급 → 줄 세우기. 이걸 별도 명령 네 개로 날리면 명령 사이에 다른 유저의 요청이 끼어든다. 상한 확인과 등록 사이를 비집고 들어와 상한이 뚫리는 식이다.

```lua
if redis.call('ZSCORE', KEYS[1], ARGV[1]) then
  return redis.call('ZRANK', KEYS[1], ARGV[1]) + 1   -- 이미 줄에 있음 → 기존 순번
end
if redis.call('ZCARD', KEYS[1]) >= tonumber(ARGV[2]) then
  return -1                                          -- 줄이 꽉 참 → 429로 변환
end
local score = redis.call('INCR', KEYS[2])            -- 새 번호 발급
redis.call('ZADD', KEYS[1], score, ARGV[1])
return redis.call('ZRANK', KEYS[1], ARGV[1]) + 1
```

Redis는 Lua 스크립트 하나를 원자적으로 실행한다. 네 단계가 한 덩어리가 되는 순간 끼어들 틈 자체가 사라진다.

> **[그림 4]** 명령 4개를 따로 보낼 때의 끼어들기 vs Lua 하나로 묶었을 때 — 원자성 비교

## 질문 3. 몇 명씩 들여보낼 것인가

다섯 질문 중 가장 오래 붙잡고 있던 것. 스케줄러가 대기열에서 유저를 꺼내 입장시키는데, **한 번에 몇 명씩, 얼마나 자주?**

"적당히 10명씩"이라고 하면 근거가 없다. 숫자는 병목에서 역산해야 한다. 이 시스템에서 대기열이 최종적으로 지키려는 자원은 **DB 커넥션 풀**이다. 거기서 출발하면 계산은 나눗셈 세 번이다.

```
DB 커넥션 풀:            40개 (HikariCP maximum-pool-size)
주문 API 몫:             50% → 20개 (상품 조회 등 다른 API와 풀 공유)
주문 평균 처리 시간 가정:  200ms (실측 전 보수적 가정)

커넥션 1개가 1초에 처리 가능한 주문 = 1000ms / 200ms = 5건
초당 입장 가능 = 20개 × 5건 = 초당 100명
```

> **[그림 5]** 배치 크기 역산 — 커넥션 풀 40 → 주문 몫 20 → 건당 200ms → 초당 100명

초당 100명이 나왔다. 그런데 여기서 결정이 하나 더 남는다. 이 100명을 **1초에 한 번 몰아넣을 것인가, 쪼갤 것인가.**

총량은 같아도 결과가 다르다. 1초에 100명을 한꺼번에 들여보내면 그 100명이 거의 동시에 주문 API를 두드린다. 커넥션 20개에 요청 100개가 일시에 도착하면 80개는 대기 행렬에 쌓인다 — 무리가 우르르 몰려드는 이 현상을 **Thundering Herd**라 부른다. 100ms마다 10명씩 쪼개면 같은 초당 100명이라도 시간축으로 분산돼 스파이크가 완만해진다.

> **[그림 6]** 1초에 100명 vs 100ms마다 10명 — 커넥션 풀 관점의 스파이크 비교

이 "시간축 분산"의 효과는 이론에 그치지 않았다. 이후 배치 내부의 동시성까지 Jitter로 한 번 더 흩뿌리고 k6로 실측했을 때 주문 API p95 지연이 6.10s → 2.42s, 60% 줄었다. 동시에 도착하는 요청 수를 줄이는 것만으로 개별 요청까지 빨라진다는 게 숫자로 확인된 셈이다. (이 실험은 분량이 있어 별도 글로 다룬다.)

덧붙여 둘 것 두 가지.

- 위 계산은 "토큰 받은 100명 전원이 즉시 주문"하는 **최악의 경우** 기준이다. 실제로는 토큰 발급 ≠ 즉시 주문이라 DB 유입은 더 완만하다. 보수적으로 시작하고 실측이 쌓이면 보정한다.
- 꺼내는 동작도 원자적이어야 한다. "앞에서 10명 조회 → 삭제"를 두 명령으로 하면 그 사이에 또 끼어들기가 생긴다. `ZPOPMIN`은 조회와 삭제가 명령 하나다.

## 질문 4. 입장권의 수명은 몇 분인가

스케줄러가 꺼낸 유저에게는 입장 토큰이 발급된다. `queue:token:{userId}` = UUID. 여기서 정할 것은 둘 — 얼마나 살아있을 것인가, 언제 죽일 것인가.

### 얼마나 — TTL 5분

토큰 수명은 "입장한 유저가 주문을 완료하는 데 필요한 시간"이어야 한다. 주문서 확인하고 결제 수단 고르기에 충분할 것. 동시에 너무 길면 안 된다 — 토큰만 받아놓고 떠난 유저가 처리량 슬롯을 오래 점유하면 그만큼 뒷사람 입장이 늦어진다. 그 균형점으로 5분.

만료 처리 코드는 없다. Redis TTL이 지우면 "키 없음 = 미발급 또는 만료"로 통일되고, 만료된 유저는 처음부터 다시 줄을 선다.

### 언제 — 주문 "성공" 시에만 삭제

처음엔 검증하면서 바로 지우는 쪽이 깔끔해 보였다. `GETDEL`이면 검증+삭제가 원자적이라 같은 토큰의 동시 사용도 원천 차단된다.

그런데 이러면 **주문에 실패한 유저가 재시도할 수 없다.** 재고 부족, 결제 실패 — 유저 잘못이 아닌 실패에서도 토큰이 증발해 처음부터 다시 줄을 서야 한다. 5분짜리 기회를 서버 사정으로 날리는 셈이다. 그래서 성공했을 때만 지우기로 했고, 이 정책은 코드 세 줄에 그대로 드러난다.

```java
entryTokenValidator.validate(userId, entryToken);   // ① 검증 (실패 → 403)
OrderInfo info = createOrder(...);                  // ② 주문 (여기서 예외 → 토큰 유지)
entryTokenValidator.consume(userId);                // ③ 성공했을 때만 삭제
```

> **[그림 7]** 토큰 생명주기 — 발급 → 검증 → (성공: 삭제 / 실패: 유지, TTL 내 재시도 / 만료: 재진입)

물론 공짜는 아니다. 같은 토큰의 동시 요청이 이론상 가능해진다. 재고 차감 로직이 최종 방어선이 된다는 걸 확인하고 허용했다 — **원자적 삭제의 깔끔함과 실패한 유저의 재시도 가능성을 맞바꾼** 트레이드오프다.

여담 하나. 검증 실패의 응답은 401이 아니라 **403**이다. 로그인은 이미 된 유저이고, 부족한 건 인증이 아니라 "입장 권한"이니까.

## 질문 5. 기다리는 유저에게 무엇을 보여줄 것인가

여기까지로 줄 세우기와 들여보내기는 끝났다. 하지만 대기열의 성패는 결국 **기다리는 경험**에 달려 있다. 아무 정보 없이 기다리게 하면 유저는 이탈하거나 새로고침을 연타한다. 은행 창구의 "대기 12명, 예상 15분" 전광판이 필요하다.

### 예상 대기 시간 — 정직한 나눗셈

처리 속도는 우리가 설정으로 통제하는 값이다: 초당 100명. 그러면 예상 대기 시간은 나눗셈 하나로 나온다.

```
estimatedWaitTime(초) = ceil(내 순번 / 100)
예: 342번째 → ceil(3.42) = 4초
단, 순번 ≤ 배치 크기(10)이면 0초 — "곧 입장"
```

"최근 N분간 실제 통과 인원"을 측정하는 동적 산정도 고려했지만, 스케줄러 처리량은 변동 요인이 적은 값이라 정적 계산으로 충분했다. 스케줄러가 멈추면 예상 시간이 틀어지는 한계는 있다 — 실제 처리량이 설정값과 크게 어긋나는 게 관측되면 그때 실측 기반으로 전환할 지점.

### pollAfter — 폴링이 서버를 공격하지 않게

계산 하나를 해보면 아찔해진다. 대기 10만 명이 2초마다 순번을 조회하면 **초당 5만 요청**. 흥미로운 건 병목의 위치다. Redis ZRANK는 O(log N)이라 이 정도는 감당한다. 먼저 무너지는 건 **톰캣 워커 스레드(기본 200개)**다. 주문 API를 지키려고 세운 대기열의, 순번 조회 API가 먼저 죽는 그림이 나온다.

그래서 응답에 다음 조회 권장 간격 `pollAfter`를 담았다. 아이디어는 단순하다 — **멀리 있는 유저일수록 자주 볼 필요가 없다.**

| 예상 대기 시간 | pollAfter |
|---|---|
| 60초 이상 | 10초 |
| 10~60초 | 5초 |
| 10초 미만 | 2초 |
| READY / NOT_IN_QUEUE | null (조회 종료) |

> **[그림 8]** 순번 구간별 pollAfter — 뒤쪽 유저는 드문드문, 임박한 유저는 자주

구간 기준을 순번이 아니라 **예상 대기 시간**으로 잡은 것도 의도다. 배치 설정이 바뀌어 처리 속도가 달라지면 pollAfter 구간이 자동으로 따라온다.

한계도 분명하다. 서버가 강제할 수 없는 클라이언트 가이드라서 커스텀 클라이언트나 봇은 무시할 수 있다. 그래도 정상 클라이언트 대다수의 조회 총량을 낮추는 것만으로 값어치를 한다.

## 답하지 않고 남겨둔 질문들

다섯 질문에 답하고 나서도, 의도적으로 미뤄둔 것들이 있다.

- **스케줄러가 두 대가 되면?** — 같은 유저를 중복으로 꺼낼 수 있다. 다중화에는 ShedLock 같은 분산 락이 필요하다. 지금은 단일 인스턴스 가정.
- **꺼낸 직후 서버가 죽으면?** — ZPOPMIN과 토큰 발급 사이에 죽으면 그 유저는 대기열에도, 토큰도 없는 상태가 된다. 두 명령을 Lua로 묶는 대신 "재진입하면 복구된다"로 허용했다. 발생 확률 대비 구현 비용을 낮춘 선택이지만 규모가 커지면 재검토.
- **Redis가 죽으면?** — 대기열 자체가 마비된다. 지금은 토큰 검증을 우회하는 kill switch(`queue.entry-token.required=false`)로 "대기열 없이라도 주문은 받는" 탈출구만 있다. 보호 장치가 단일 장애점이 되는 아이러니 — Graceful Degradation은 다음 과제다.
- **같은 배치 10명의 동시 도착은?** — 100ms로 쪼개도 같은 틱의 10명은 동시에 온다. Jitter로 흩뿌린 실험(p95 60% 개선)과 Polling 대신 SSE로 순번을 push하는 실험은 각각 별도 글로.

## 다시 대기열을 만들게 된다면

이번 설계를 통과하며 만든, 다음에 스스로에게 던질 체크리스트로 글을 맺는다.

- [ ] 이 요청은 유저에게 **기회**인가, 소음인가? — 기회면 줄 세우고, 소음이면 잘라낸다. 그리고 줄에도 상한은 필요하다.
- [ ] 순번의 기준은 **단일한가**? — 서버 시계처럼 여러 개일 수 있는 것을 기준으로 삼고 있지 않은가.
- [ ] 들여보내는 숫자에 **역산 근거**가 있는가? — 병목 자원에서 출발한 나눗셈인가, 감인가. 근거 없는 숫자는 바꿀 때도 감으로 바꾸게 된다.
- [ ] 확인-후-행동 패턴이 있다면 **원자적인가**? — 확인과 행동 사이는 언제나 끼어들기의 틈이다.
- [ ] 유저 잘못이 아닌 실패에서 **재시도가 가능한가**? — 깔끔한 원자성보다 중요할 때가 있다.
- [ ] 기다리는 유저가 **예측할 수 있는가**? — 순번, 예상 시간, 조회 주기. 대기열 설계의 절반은 기다리는 경험 설계였다.
