# 대기열 시스템 — Redis Sorted Set + 토큰 스케줄러 + Jitter + SSE

## 🧭 Context & Decision

### 문제 정의
- **현재 동작/제약**: 블랙프라이데이 같은 순간적 대규모 트래픽이 그대로 주문 API에 진입하면 커넥션 풀이 고갈되고 500/503으로 무너진다. 먼저 클릭했어도 커넥션 경쟁에서 밀리면 실패한다.
- **문제(리스크)**: Rate Limiting으로 초과분을 429로 자르면 시스템은 지키지만 유저가 **주문 기회 자체를 잃는다**. 대기열은 이 기회를 보존하지만, 순서 보장·상태 조회·토큰 검증·스파이크 완화·실시간성 등 복합 문제를 동시에 해결해야 한다.
- **성공 기준**: (1) 시스템이 감당할 수 있는 속도로만 주문 API에 진입 (2) 진입 순서가 보장되고 유저는 예상 시간을 안다 (3) 토큰이 발급된 후 같은 배치가 몰려 스파이크를 만들지 않는다 (4) 재시작·재접속·중복 진입에 견고하다.

---

### 선택지와 결정

**[결정 1] 초과 트래픽 처리 — Rate Limit vs 대기열**

- 고려한 대안:
  - A (아무것도 없음): 그대로 받다 500/503, 커넥션 운에 따라 성공/실패
  - B (Rate Limiting): 초당 허용 초과분 즉시 429
  - C (대기열): 거부하지 않고 줄 세우기
- 최종 결정: **C를 기본으로 두되, C 뒤에 상한(429)을 한 겹 더 두는 조합**
- 트레이드오프:
  - A는 커넥션 경쟁이 그대로 노출되어 "먼저 클릭한 유저가 반드시 성공하지도 못하는" 최악의 형태다. 서비스 관점에서 폴백이 아니라 실패다.
  - B는 시스템 부하는 확실히 제한되지만 거부당한 유저가 재시도하거나 이탈해 **주문 기회 자체를 잃는다**. 429는 "지금 다시 눌러라"라는 신호에 가까운데, 순간 트래픽이 지속되면 재시도가 다시 429를 받아 유저 경험이 무너진다. 티켓팅·수강신청처럼 **기회의 재분배가 어려운 상황**에서는 부적합하다.
  - C는 거부하지 않고 순서를 보존한다. 대신 저장소(Redis)와 스케줄러가 필요하고 구현 복잡도가 크게 올라간다. 그리고 대기열도 무한히 커지면 Redis 메모리가 위험해지므로 **결국 상한이 필요**하고, 상한 초과분은 다시 429로 거부해야 한다.
  - 즉 실제 구조는 "Rate Limit vs 대기열"의 양자택일이 아니라 **"대기열 뒤에 Rate Limit을 한 겹 더 둔" 계층 구조**가 된다. 대기열은 "초과분을 나중에 처리"하고, 마지막 상한선은 여전히 "초과분을 잘라내는" 역할을 한다.

**[결정 2] 중복 진입 정책 — 밀림 vs 기존 순번 유지**

- 고려한 대안:
  - A ("새로고침 시 밀림"): 재요청 시 뒤로 재배치 — 티켓팅 서비스 전통 정책
  - B ("기존 순번 유지"): 재요청 무시(`ZADD NX`)
- 최종 결정: **B**
- 트레이드오프:
  - A는 극단적 트래픽 억제엔 유리하다. "새로고침 = 손해"라는 신호를 주면 유저가 새로고침을 자제하고 서버가 받는 실제 요청 수가 급감한다. 티켓팅처럼 **공급이 극단적으로 부족하고 봇·매크로가 만연한 도메인**에서는 여전히 유효한 정책이다.
  - 문제는 A가 정상 유저까지 벌한다는 점이다. 네트워크가 불안정해 재전송이 일어난 유저, 브라우저가 죽어 재접속한 유저, "지금 몇 번째지?"를 확인하려 새로고침한 유저 모두 밀린다. 이커머스 주문은 티켓팅만큼 공급이 부족하지 않고, 유저 신뢰가 재구매율로 이어지는 도메인이라 **"실수해도 안전하다"는 신호가 더 중요**하다.
  - B는 트래픽 억제 효과가 없다는 단점이 있지만, 실제로 억제해야 할 만큼의 트래픽이 발생하면 [결정 1]의 상한(429)이 방어한다. 정책 하나로 두 문제(신뢰·트래픽)를 다 잡으려 하지 않고, 트래픽은 상한, 신뢰는 중복 정책이 각각 담당하는 구조로 나눴다.

**[결정 3] 배치 크기·주기 산정 — 커넥션 풀 기반 역산**

- 최종 결정: **100ms 주기 / 배치 10명 (= 초당 100명)**
- 산정 근거:
  ```
  DB 커넥션 풀 40 × 주문 API 몫 50% = 주문에 쓸 커넥션 20개
  주문 평균 처리 200ms 가정
  초당 입장 = 20 × (1000 / 200) = 100명
  → 100ms마다 10명씩 쪼갬
  ```
- 트레이드오프:
  - "초당 100명"이라는 총량은 커넥션 풀에서 역산했다. 이 총량을 어떻게 시간축에 분배할지가 실제 결정이다.
  - "1초에 한 번 100명"으로 하면 매초 초입에 100명이 몰려 **주문 API가 초당 스파이크**를 만든다. 커넥션 풀은 순간적으로 100% 사용되고 lock 경합이 커지며 뒤 유저는 큐잉된다. 한꺼번에 몰리는 전형적인 스파이크 패턴이다.
  - "100ms에 10명"으로 쪼개면 같은 총량이 시간축에 10배 넓게 퍼진다. 커넥션 풀 사용률이 완만하게 유지되고 배치 내 경합이 줄어든다 — 아래 Jitter 실측이 이 효과를 뒷받침한다.
  - 더 잘게 쪼갤 수도 있다(10ms/1명 등). 하지만 스케줄러 호출 오버헤드가 상대적으로 커지고, 실제 주문 처리는 이보다 느리게 이뤄져 스케줄러가 그만큼 정밀하게 동작할 필요가 없다. 100ms는 "한꺼번에 몰리는 현상을 막을 만큼 잘고, 스케줄러 오버헤드는 무시할 만한" 지점.
  - 위 수치는 **"토큰 받자마자 전원 즉시 주문"**이라는 최악 케이스 기준. 실제로는 토큰 받은 뒤 주문서 검토·결제 수단 선택 등으로 유입이 분산돼 이보다 훨씬 여유롭다. 그래서 이 산정은 "최악의 경우를 가정한 상한값"이지 정확한 목표치가 아니다. 실측 데이터가 쌓이면 보정한다.

## 📊 Jitter 실측 — Before/After

이론으로 결정한 500ms Jitter가 실제로 어떤 차이를 만드는지 k6로 검증했다. 100 유저 동시 진입, 재고 10만 조건.

| 지표 | Before (jitter=0) | After (jitter=500) | 개선 |
|---|---|---|---|
| order_latency avg | 4.94s | 1.99s | −60% |
| order_latency p50 | 5.25s | 2.20s | −58% |
| order_latency p95 | 6.10s | 2.42s | −60% |
| order_latency max | 7.08s | 2.63s | −63% |
| total_latency p95 | 9.52s | 5.01s | −47% |
| 성공률 | 100/100 | 100/100 | — |

**알게 된 것 1 — 성공률만 봐서는 Jitter 효과가 안 보인다.** 두 케이스 모두 100/100 성공이지만 지연 분포가 완전히 다르다. Jitter 없을 때 어떤 유저는 1.15s만에 끝나고 어떤 유저는 7.08s를 기다렸다. SLO는 tail latency로 정의되고 알럿도 tail 기준이라 max·p95 감소가 실제 사용자 경험을 결정한다.

**알게 된 것 2 — Jitter가 개인을 늦추는데 총 시간은 오히려 줄었다.** `total_latency` p95가 9.52s → 5.01s로 4.5초 짧아졌다. Jitter는 각 유저를 최대 500ms 지연시키는데 왜 개인 총 시간이 짧아질까? **주문 API가 빨라지기 때문**이다. 배치 내 경합이 줄면 배치 하나가 빨리 소화되고 다음 배치 유저의 대기 시간도 함께 짧아진다. 개인이 500ms 참는 대가로 전체 처리가 빨라진 결과가 개인에게도 돌아온다.

## 🤔 고민한 점 / 막혔던 부분

**500ms가 실측 최적인지는 아직 모른다.** 실측이 보여주는 건 "500ms가 100 유저 규모에서 확실히 효과가 있다"이지 "500ms가 최적이다"가 아니다. 200ms·1s로 곡선을 그려야 최적 지점을 안다. 100 유저는 배치 몇 번이면 끝나는 소규모라 초당 수천 요청 규모에서는 곡선 모양이 달라질 수도 있다 — 커넥션 풀이 지속 포화되면 Jitter 효과가 더 커질 수도 있고, 반대로 다른 병목(DB 락)이 지배적이 되어 잘 안 보일 수도 있다. 이번 실측은 "이 방향이 맞다"의 근거이지 "이 값이 정답"의 근거는 아니다.
