# 실시간 랭킹 — Redis ZSET + Kafka Consumer 파생 뷰

## 🧭 Context & Decision

### 문제 정의
- **현재 동작/제약**: Kafka Consumer가 조회·좋아요·주문 이벤트를 컨슘해 `product_metrics`(MySQL)에 **누적 카운트**를 적재하고 있다. 하지만 누적 카운트는 일자 구분이 없어 "오늘의 인기상품"을 뽑을 수 없고, 매 조회마다 집계·정렬을 돌리면 비싸다.
- **문제(리스크)**: 실시간 랭킹은 "같은 사건을 MySQL과 Redis 두 곳에 적어야 하는" 이중 쓰기, "같은 메시지가 두 번 배달되는" 멱등성, "날짜별 키가 무한히 쌓이는" 메모리 문제를 동시에 안는다. 강한 즉시 일관성을 맞추려 하면 2일이면 버려질 데이터에 과투자하게 된다.
- **성공 기준**: (1) 이벤트가 발생하면 ZSET에 점수가 반영돼 랭킹 Page·상품 상세 순위로 조회된다 (2) 재배달·재시작에도 점수가 중복 가산되지 않는다 (3) 날짜가 바뀌어도 과거 랭킹 조회가 정상 동작한다.

### 선택지와 결정

전제를 먼저 세웠다 — **Redis 랭킹은 "파생 뷰"다.** 진실의 원천은 `product_metrics`(MySQL)이고 ZSET은 그것을 빠르게 보여주는 파생 캐시일 뿐이며, 키는 TTL 2일이라 애초에 버려진다. MySQL 집계 데이터가 창고의 실제 판매 원장이라면, Redis 랭킹은 매장 입구의 "오늘의 베스트" 진열대다. 진열 순서가 조금 틀려도 판매 원장만 정확하면 언제든 다시 진열하면 된다. 아래 세 결정은 모두 이 관점에서 나온다 — **랭킹은 약간 틀려도 치명적이지 않고, MySQL 기준으로 재구성(rebuild)해 자가 치유할 수 있다.**

**[결정 1] TTL — 최초 1회만 EXPIRE vs 매 이벤트 갱신**

- 고려한 대안:
  - A (매 이벤트마다 EXPIRE 갱신): `ZINCRBY` 후 항상 `EXPIRE key 2d`
  - B (키 최초 생성 시 1회만): 키가 새로 만들어질 때만 EXPIRE
- 최종 결정: **A (매 이벤트마다 EXPIRE 갱신)**
- 트레이드오프:
  - `ZINCRBY`는 점수만 더할 뿐 이 진열대를 언제 내릴지(EXPIRE)는 정해주지 않으므로 우리가 명시적으로 걸어야 한다. 안 걸면 날짜별 진열대가 매일 쌓여 Redis 메모리를 계속 잡아먹는다.
  - B는 명령을 최소화하지만, 그 한 번의 EXPIRE가 실패·경합으로 누락되면 키가 영영 안 지워져 메모리 누수가 된다. "이 키가 방금 새로 생겼나?"를 판단하는 경합 처리도 필요하다.
  - A는 이번 EXPIRE가 실패해도 **다음 이벤트가 다시 걸어준다** — 파생 뷰의 "틀어져도 다음에 보정" 철학과 동일하다. 분기도 경합도 없이 무조건 EXPIRE를 걸고, 비용은 `ZINCRBY` 옆에 명령 하나 추가라 사실상 없다(파이프라인/Lua로 묶으면 왕복 1회).
  - 슬라이딩 윈도우 우려는 키가 `ranking:all:{yyyyMMdd}`로 날짜 고정이라 해소된다. 오늘 키의 마지막 이벤트는 늦어야 23:59 → 모레 23:59까지 유지되어 **"이전 날짜 랭킹도 정상 조회"** 요구사항을 오히려 확실히 만족한다.
  - 구현: `incrementScore`에서 `ZINCRBY` 후 `expire(key, 2d)`. (`RankingRedisRepositoryImpl`)

**[결정 2] 콜드 스타트 완화 — 백지로 시작 vs 감쇠 Carry-Over**

- 고려한 대안:
  - A (감쇠 Score Carry-Over): 23:50에 오늘 Top-N을 감쇠(×0.1)해 내일 키에 밑그림으로 `ZADD`
  - B (완화 없음 / 어제 점수 그대로 복사): 자정에 백지(0점)로 시작하거나, 어제 점수를 감쇠 없이 그대로 넘김
- 최종 결정: **A (감쇠 Carry-Over)**
- 트레이드오프:
  - 일간 키는 자정에 텅 빈 백지(0점)로 새로 열린다. 새벽엔 트래픽이 적어 손님 한 명의 조회(+0.1)가 곧바로 1등이 되는 믿기 어려운 순위(콜드 스타트)가 된다.
  - B의 "백지 시작"은 이 문제를 그대로 방치한다. 반대로 "어제 점수 그대로 복사"는 콜드 스타트는 없애지만, 어제 1등이 관성으로 오늘도 계속 1등이라 신흥 인기가 못 올라온다(고인물). 그래서 **감쇠(×0.1)** 해 출발선 어드밴티지만 주고 실제 승부는 오늘 이벤트로 가린다.
  - **혼동 주의 — Carry-Over ≠ 어제 랭킹 조회.** 가져온 어제 점수는 *보여주려는 데이터가 아니라 오늘의 출발점(prior)*이다. "어제자 랭킹 조회"(`?date=어제`)는 어제 진열대를 그대로 노출하는 확정·불변 데이터고, Carry-Over는 오늘 이벤트가 쌓이면 덮여 사라지는 초기 밑그림이다.
  - 소스는 **오늘 Redis ZSET Top-N**(`ZREVRANGE`)이다 — `product_metrics`(MySQL)는 누적 카운트라 일자 구분이 없어, 일간 점수를 가진 유일한 곳이 오늘 Redis 키다. 쓰기는 내일 키가 아직 비어 있을 때 `ZADD`(절대·멱등)라 스케줄러가 두 번 돌거나 인스턴스가 여럿이어도 결과가 동일해 별도 락이 필요 없다.
  - 구현: 23:50 `@Scheduled`에서 오늘 Top-N을 ×DECAY로 내일 키에 `ZADD`, 감쇠계수·N은 `ranking.carryover.*` 설정으로 조절. (`RankingCarryOverService`)

**[결정 3] 시간 단위 실시간 랭킹 — 조회 시 즉석 합산 vs 분 버킷 + 사전 합산**

- 고려한 대안:
  - A (분 버킷 + 1분 사전 합산): 이벤트를 1분 버킷(`ranking:min:{yyyyMMddHHmm}`)에 쪼개 담고, 1분마다 최근 60개 버킷을 `ZUNIONSTORE`해 조회용 롤링 키(`ranking:hourly:current`)에 미리 합산
  - B (조회 시 즉석 합산): 조회가 들어올 때마다 최근 60개 분 버킷을 그 자리에서 union
- 최종 결정: **A (분 버킷 + 사전 합산)**
- 트레이드오프:
  - "지난 1시간 인기상품"은 시간이 흐르면 창이 미끄러지는(sliding) 랭킹이다. 이를 구현하려면 시간을 **양자화**해야 한다 — 이벤트를 1분 봉투에 나눠 담으면 "최근 60개 봉투"만 더해 윈도우를 만들고, 오래된 봉투는 창 밖으로 자연히 빠진다.
  - B는 항상 최신이지만, 조회마다 60개 키를 union하는 비용을 **사용자 요청 경로에 얹는다.** 트래픽이 몰리면 이 합산이 그대로 지연·부하가 된다.
  - A는 합산을 조회 경로에서 떼어내 **1분마다 미리** 한 판(`ranking:hourly:current`)에 저장한다(사전 합산). 조회는 이 단일 키만 읽어 O(1)이고, 최대 1분 낡은 값이지만 "지난 1시간"이라는 창에서 1분 오차는 무의미하다.
  - 사전 합산은 `ZUNIONSTORE`로 판을 통째로 재생성하는 **덮어쓰기**라 여러 인스턴스가 동시에 돌아도 결과가 같다(멱등) → 별도 락이 필요 없다. 실패해도 best-effort로 넘기고 다음 1분 주기가 다시 합산한다 — 결정 1의 "틀어져도 다음에 보정" 철학과 동일하다.
  - 조회용 롤링 키 TTL은 **2분**으로 짧게 둔다 — 스케줄러가 죽으면 낡은 판을 오래 노출하지 않고 자연 만료되게 하기 위함이다. (윈도우에 여유를 준 분 버킷 TTL은 2h.)
  - 구현: write는 이벤트 시 일간 키 + 현재 분 버킷에 fan-out `ZINCRBY`(`RankingEventListener`), 사전 합산은 `@Scheduled(fixedRate=60s)`에서 `unionInto`(`RankingHourlyAggregator`). 윈도우 길이는 `ranking.hourly.windowMinutes` 설정.
