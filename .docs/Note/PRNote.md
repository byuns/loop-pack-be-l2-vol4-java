# 실시간 랭킹 — Redis ZSET + Kafka Consumer 파생 뷰

## 🧭 Context & Decision

### 문제 정의
- **현재 동작/제약**: Kafka Consumer가 조회·좋아요·주문 이벤트를 컨슘해 `product_metrics`(MySQL)에 **누적 카운트**를 적재하고 있다. 하지만 누적 카운트는 일자 구분이 없어 "오늘의 인기상품"을 뽑을 수 없고, 매 조회마다 집계·정렬을 돌리면 비싸다.
- **문제(리스크)**: 실시간 랭킹은 "같은 사건을 MySQL과 Redis 두 곳에 적어야 하는" 이중 쓰기, "같은 메시지가 두 번 배달되는" 멱등성, "날짜별 키가 무한히 쌓이는" 메모리 문제를 동시에 안는다. 강한 즉시 일관성을 맞추려 하면 2일이면 버려질 데이터에 과투자하게 된다.
- **성공 기준**: (1) 이벤트가 발생하면 ZSET에 점수가 반영돼 랭킹 Page·상품 상세 순위로 조회된다 (2) 재배달·재시작에도 점수가 중복 가산되지 않는다 (3) 날짜가 바뀌어도 과거 랭킹 조회가 정상 동작한다.

### 선택지와 결정

전제를 먼저 세웠다 — **Redis 랭킹은 "파생 뷰"다.** 진실의 원천은 `product_metrics`(MySQL)이고 ZSET은 그것을 빠르게 보여주는 파생 캐시일 뿐이며, 키는 TTL 2일이라 애초에 버려진다. MySQL 집계 데이터가 창고의 실제 판매 원장이라면, Redis 랭킹은 매장 입구의 "오늘의 베스트" 진열대다. 진열 순서가 조금 틀려도 판매 원장만 정확하면 언제든 다시 진열하면 된다. 아래 세 결정은 모두 이 관점에서 나온다 — **랭킹은 약간 틀려도 치명적이지 않고, MySQL 기준으로 재구성(rebuild)해 자가 치유할 수 있다.**

**[결정 1] 이중 쓰기 정합성 — 트랜잭션 내 반영 vs 커밋 후 best-effort**

- 고려한 대안:
  - A (커밋 후 best-effort + 재구성): MySQL 커밋 성공 후에만 `ZINCRBY`(afterCommit), 실패 시 로그 + rebuild로 자가 치유
  - B (트랜잭션 내 동기 반영): `@Transactional` 안에서 `ZINCRBY` 호출
- 최종 결정: **A (커밋 후 best-effort + 재구성)**
- 트레이드오프:
  - B는 코드가 직관적이지만, Redis는 트랜잭션의 되돌리기(undo)에 낄 수 없다. Redis 먼저 성공 → MySQL 커밋 실패 시 **진열대에만 +600이 남는 과다 집계**가 되고, rebuild 없이는 어디가 틀렸는지 알 수 없어 자가 치유가 안 된다. 게다가 Redis 장애가 집계 파이프라인 전체를 멈춰 세운다 — 파생 캐시 때문에 본체(판매 원장 기록)까지 볼모로 잡히는 나쁜 거래.
  - A는 순서를 **"MySQL 커밋 성공 후 Redis"**(afterCommit)로 고정해 실패해도 **과소 집계**로만 끝나게 한다. 과소는 rebuild로 채울 수 있지만 과다는 복구가 어렵다 — 과다보다 과소가 안전하다. 단, A는 rebuild 경로가 반드시 존재해야 성립하는데, 이는 콜드 스타트 Carry-Over 스케줄러와 같은 machinery라 자연스럽게 확보된다.
  - 구현: `@TransactionalEventListener(AFTER_COMMIT)`로 `ZINCRBY`, 실패는 `log.warn`만. (`RankingEventListener`)

**[결정 2] 멱등성 — 별도 Redis 추적 vs event_handled 게이트 재사용**

- 고려한 대안:
  - A (event_handled 게이트가 Redis 멱등성까지 책임): 이미 있는 이벤트면 MySQL·Redis 둘 다 건드리지 않음
  - B (별도 "Redis 반영 추적" 테이블): Redis 반영 여부를 따로 추적
- 최종 결정: **A (event_handled 게이트 재사용, 별도 추적 없음)**
- 트레이드오프:
  - Kafka는 컨슈머 재시작·리밸런싱·재시도로 **같은 메시지를 다시 배달**한다. MySQL 쪽은 이미 `event_handled`("처리한 사건 목록")로 방어돼 있지만, `ZINCRBY`는 "현재값에 더하기"라 두 번 부르면 그대로 두 배가 된다.
  - B는 결정 1에서 버린 안(별도 추적)과 사실상 같다. 2일이면 사라질 순위판을 위해 추적 상태·경합 관리를 또 만드는 과투자.
  - A는 결정 1의 흐름에 규칙 하나만 얹으면 끝난다 — **Redis 점수 반영은 "이번에 새로 처리된 이벤트"에만 건다.** afterCommit 등록 자체를 dedup 체크를 통과한 새 이벤트 분기 안에서만 수행하면, "처리한 사건 목록" 문지기 하나가 MySQL과 Redis 양쪽의 중복을 동시에 막는다. 좋아요 취소(-0.2)의 이중 차감도 같은 게이트가 막는다.
  - 단점은 "커밋 후 Redis 직전 크래시 → 재배달" 시 게이트가 skip해 Redis가 그 건을 놓치는 **과소 집계**인데, 이는 결정 1에서 이미 수용한 트레이드오프이며 rebuild로 보정한다.
  - 구현: `existsByEventId` → 신규면 `event_handled` 기록 + metrics 갱신 후에만 `publishEvent(RankingScoreEvent)`. (`ViewAggregatorService`)

**[결정 3] TTL — 최초 1회만 EXPIRE vs 매 이벤트 갱신**

- 고려한 대안:
  - A (매 이벤트마다 EXPIRE 갱신): `ZINCRBY` 후 항상 `EXPIRE key 2d`
  - B (키 최초 생성 시 1회만): 키가 새로 만들어질 때만 EXPIRE
- 최종 결정: **A (매 이벤트마다 EXPIRE 갱신)**
- 트레이드오프:
  - `ZINCRBY`는 점수만 더할 뿐 이 진열대를 언제 내릴지(EXPIRE)는 정해주지 않으므로 우리가 명시적으로 걸어야 한다. 안 걸면 날짜별 진열대가 매일 쌓여 Redis 메모리를 계속 잡아먹는다.
  - B는 명령을 최소화하지만, 그 한 번의 EXPIRE가 실패·경합으로 누락되면 키가 영영 안 지워져 메모리 누수가 된다. "이 키가 방금 새로 생겼나?"를 판단하는 경합 처리도 필요하다.
  - A는 이번 EXPIRE가 실패해도 **다음 이벤트가 다시 걸어준다** — 결정 1·2의 "틀어져도 다음에 보정" 철학과 동일하다. 분기도 경합도 없이 무조건 EXPIRE를 걸고, 비용은 `ZINCRBY` 옆에 명령 하나 추가라 사실상 없다(파이프라인/Lua로 묶으면 왕복 1회).
  - 슬라이딩 윈도우 우려는 키가 `ranking:all:{yyyyMMdd}`로 날짜 고정이라 해소된다. 오늘 키의 마지막 이벤트는 늦어야 23:59 → 모레 23:59까지 유지되어 **"이전 날짜 랭킹도 정상 조회"** 요구사항을 오히려 확실히 만족한다.
  - 구현: `incrementScore`에서 `ZINCRBY` 후 `expire(key, 2d)`. (`RankingRedisRepositoryImpl`)

## 📊 가중치 산정 — 왜 log 정규화인가

세 신호(조회·좋아요·주문)를 한 판에서 겨루게 하려면 **스케일을 맞춰야** 한다. 요구사항 예시(점수 = Weight × Score)를 그대로 쓰면 주문 항만 자릿수가 폭발한다.

| | 조회 | 좋아요 | 주문 | 원시 점수 |
|---|---|---|---|---|
| 상품 A | 1000 | 100 | 0 | 1000×0.1 + 100×0.2 = **120** |
| 상품 B | 1 | 0 | 20만원 1개 | 0.6×200000 = **120,000** |

딱 한 명이 산 B가 조회 1000·좋아요 100의 A를 **1000배**로 눌러버린다. "진짜 인기상품"과 거리가 먼 롱테일 문제다. 그래서 **주문 금액만 log10으로 정규화**했다.

```
조회   score += 0.1
좋아요 score += 0.2   (취소 시 -0.2)
주문   score += 0.6 × log10(1 + price × amount)
```

| 주문 금액 | 원시값 | log10(1+금액) |
|---|---|---|
| 1,000원 | 1,000 | ≈ 3.0 |
| 10,000원 | 10,000 | ≈ 4.0 |
| 100,000원 | 100,000 | ≈ 5.0 |
| 1,000,000원 | 1,000,000 | ≈ 6.0 |

**알게 된 것 1 — 가중치만 낮추는 걸로는 안 된다.** 여전히 선형이라 지배 구도가 그대로고 전체 점수만 작아진다. 상한선(cap)은 특정 금액에서 뚝 끊기는 절벽을 만든다. log는 "곱셈으로 벌어지는 차이를 덧셈으로 눌러주는" 자라 1천원~1천만원의 10,000배 범위를 3.0~7.0(약 2.3배)로 눌러 **절벽 없이 부드럽게** 완만해진다.

**알게 된 것 2 — 순서만 필요하므로 double을 그대로 쓴다.** log 점수는 `3.18` 같은 double이지만 랭킹은 순서만 필요해 부동소수점 미세 오차가 순위를 뒤집지 않는다. 정수 스케일링 없이 그대로 ZSET score로 쓴다. 가중치 0.1/0.2/0.6은 `ranking.weight` 설정으로 빼 재배포 없이 조절 가능하게 했다.

## 🤔 고민한 점 / 막혔던 부분

**콜드 스타트를 "어제 랭킹 조회"와 혼동하지 않기.** 일간 진열대는 자정에 텅 빈 매대(0점)로 새로 여는데, 새벽엔 손님 한 명의 조회(+0.1)가 곧바로 1등이 되는 믿기 어려운 순위가 된다. 이를 완화하려 23:50에 오늘 Top-N을 감쇠해 내일 진열대에 미리 깔아두는 Score Carry-Over를 넣었는데(`RankingCarryOverService`), 여기서 헷갈리기 쉬운 지점이 있었다 — 가져온 어제 점수는 **보여주려는 데이터가 아니라 오늘의 출발점(prior)**이다. "어제자 랭킹 조회"는 어제 진열대를 그대로 노출하는 확정·불변 데이터고(`?date=어제`), Carry-Over는 오늘 이벤트가 쌓이면 덮여 사라지는 초기 진열이다. 그대로 복사하지 않고 감쇠(×0.1)하는 이유도 여기 있다 — 그대로 넘기면 어제 1등이 관성으로 오늘도 계속 1등이라 신흥 인기가 못 올라온다. 감쇠는 출발선 어드밴티지만 주고 실제 승부는 오늘 이벤트로 가린다. 쓰기는 내일 키가 아직 비어 있을 때 `ZADD`(절대·멱등)라 스케줄러가 두 번 돌거나 인스턴스가 여럿이어도 결과가 동일해 별도 락이 필요 없다.
