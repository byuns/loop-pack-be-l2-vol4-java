# 주간/월간 랭킹 — Spring Batch 집계 + Materialized View 조회

## 🧭 Context & Decision

### 문제 정의
- **현재 동작/제약**: 일간·시간 랭킹은 이벤트가 올 때마다 Redis ZSET을 증분 갱신하는 **실시간** 방식으로 처리 중이다. 하지만 주간·월간은 성격이 다르다 — 매 조회마다 `product_metrics`(MySQL)의 수십만 행을 실시간으로 합산·정렬할 수 없다.
- **문제(리스크)**: 대량 데이터를 조회 경로에서 집계하면 응답이 그대로 느려지고 DB에 부하가 쏠린다. 또 우리 점수식은 `view·wv + like·wl + log10(1+sales)·wo`처럼 **여러 카운트의 가중합**이라 단순 컬럼 하나로 `ORDER BY` 할 수 없는데, TOP 100 순위는 **전체를 정렬해봐야** 나온다. 이걸 조각내어 흘려보내는(chunk) 배치 구조에서 어떻게 안전하게·중복 없이 매기느냐가 관건이다.
- **성공 기준**: (1) 주간·월간 TOP 100이 미리 계산돼 조회 시 조인·집계 없이 rank 순으로 페이지만 읽으면 된다 (2) 배치가 몇 번을 돌거나 중간에 죽어도 결과가 같다(멱등) (3) `?period=daily|weekly|monthly`로 소스를 갈라 조회하되 기존 daily API는 하위호환을 유지한다.

### 선택지와 결정

전제를 먼저 세웠다 — **읽기/쓰기 부하를 시간축으로 분리한다.** 무거운 집계는 미리·한 번에 굽고(배치), 조회는 그 결과판을 가볍게 읽기만 한다(MV). 실시간 랭킹이 매장 입구의 "지금 이 순간" 진열대라면, 주간·월간 MV는 **정해진 기간의 확정 판을 미리 인쇄해 둔 벽보**다. 벽보는 매번 다시 계산하지 않고 정해진 주기에 새로 인쇄해 갈아 끼운다. 아래 세 결정은 모두 이 관점에서 나온다 — **진실의 원천은 `product_metrics`(MySQL)이고, MV는 그것을 조회에 최적화해 재구성(rebuild)한 파생 판이라 언제든 다시 구우면 된다.**

**[결정 1] TOP-N 전역 순위 — Reader가 SQL로 점수순 정렬 vs 2단계 Step**

- 고려한 대안:
  - A (Reader가 SQL로 점수순 정렬): native SQL로 점수식을 계산해 `ORDER BY score DESC LIMIT 100` → 이미 정렬된 채로 흘려보내고, Processor는 흘러온 순서대로 rank 1,2,3… 부여
  - B (2단계 Step): Step1에서 전체를 staging 테이블에 점수 적재 → Step2에서 점수순으로 읽어 rank 부여
- 최종 결정: **A (Reader가 SQL로 점수순 정렬)**
- 트레이드오프:
  - Chunk는 데이터를 조금씩 흘려보내는 **스트리밍** 구조라, 청크를 넘나드는 전역 rank를 앱 메모리에서 매기기 까다롭다. 전체를 다 들고 정렬하면 chunk를 쓰는 의미가 없어진다.
  - B는 점수식을 코드 한 곳에만 두고(중복 제거) 단계별로 깔끔하게 나눌 수 있지만, staging 테이블·Step이 추가돼 복잡도가 올라간다. 2일이면 새로 구울 파생 판에 이만한 구조를 얹는 건 과투자다.
  - A는 **DB가 잘하는 일(정렬·LIMIT)을 DB에 맡기고** 앱은 rank 부여만 한다. Reader가 점수 내림차순으로 흘려주므로 단일 스레드 Chunk에서 Processor가 `AtomicInteger`로 `++rank`만 하면 되고, Processor를 `@StepScope`로 두면 Step 실행마다 새 인스턴스라 카운터가 0부터 다시 시작(멱등)한다.
  - 대가는 **점수식이 SQL(정렬용)과 코드(`RankingScorePolicy`, 저장용) 두 곳에 산다**는 것 — 둘이 어긋나면 순위가 틀어진다. 이 의도적 결합을 코드 주석으로 명시해 방어했다. (`RankItemReader`, `RankItemProcessor`)

**[결정 2] MV 재적재 — 비우고 새로 굽기(clear+aggregate) vs 증분 upsert**

- 고려한 대안:
  - A (비우고 새로 굽기): Job을 `[clearStep(Tasklet)] → [aggregateStep(Chunk)]` 2단계로 구성해, 매번 대상 MV를 통째로 비우고 새로 적재
  - B (증분 upsert): 기존 MV 행을 rank·score로 갱신하며 필요분만 덮어씀
- 최종 결정: **A (비우고 새로 굽기)**
- 트레이드오프:
  - TOP 100은 순위가 통째로 뒤바뀔 수 있어 어제 4등이 오늘 랭킹 밖으로 빠지기도 한다. B의 증분 upsert는 이렇게 **빠져야 할 잔여 행**을 정교하게 지워야 하고, 실패 지점에 따라 낡은 rank가 섞이는 부분 갱신 위험을 안는다.
  - A는 **덮어쓰기라 몇 번을 돌려도 결과가 같다(멱등)** — 배치가 두 번 실행되거나 중간에 죽어도, 다음 실행이 판을 새로 구우면 그대로 회복된다. "틀어져도 다음에 보정"이 아니라 아예 "매번 백지에서 확정"하는 방식이라 잔여 상태를 걱정할 필요가 없다.
  - 대가는 재적재 순간 MV가 잠깐 비는 구간이 생긴다는 것이지만, 주간·월간 랭킹은 분 단위 지연이 무의미한 성격이라 감수했다. (`RankClearTasklet` → `aggregateStep`)

**[결정 3] 점수 정책 — 실시간 정책 재사용 vs 카운트 기반 재설계**

- 고려한 대안:
  - A (카운트 기반으로 새로 설계): batch가 자기 `RankingScorePolicy` 사본을 갖고, `product_metrics`의 카운트만으로 점수식을 다시 세움
  - B (streamer의 실시간 정책 그대로 재사용): 이벤트 1건을 점수화하던 기존 식을 batch에서도 호출
- 최종 결정: **A (카운트 기반 재설계)**
- 트레이드오프:
  - 실시간 정책은 `orderScore = wo × log10(1 + price×quantity)`처럼 주문 **"금액"**을 점수화했다. 그런데 배치가 읽는 `product_metrics`엔 카운트만 있고(`sales_count`) **금액이 없다** → B는 애초에 그대로 호출할 수 없다.
  - A는 소스가 가진 데이터에 맞춰 `score = view·wv + like·wl + log10(1+sales)·wo`로 다시 세운다. 조회·좋아요는 선형, 판매는 `log10(1+n)`으로 완만하게 정규화해 한 상품의 대량 판매가 순위를 부수지 않게 했다.
  - **가중치(`ranking.weight`) 설정은 재사용**하고 계산식만 상황에 맞게 교체 — 값은 공유, 식은 분리다. 앱 분리 컨벤션대로 batch가 streamer와 별개의 정책 사본을 보유하며, 이는 결정 1의 점수식 중복과 같은 결(앱 간 결합↓ ↔ 개념 사본↑)의 트레이드오프다.
  - **정직한 한계**: `product_metrics`는 상품당 누적 1행(product_id UNIQUE)이라 날짜 차원이 없다 → 지금은 "현재 스냅샷 재집계"라 가중치가 같으면 주간·월간 순위가 동일해진다. 실무화하려면 일자별 스냅샷 테이블이 선행돼야 한다. (`RankingScorePolicy`)

## 🙋 기타

- **API 확장**: `?period=daily|weekly|monthly`로 소스를 라우팅한다. daily는 Redis ZSET(실시간), weekly/monthly는 MV(DB). daily는 rank를 조회 위치(offset+i+1)로 계산하지만 **MV는 rank가 이미 저장돼 있어** 그대로 써서 더 정확하다. 잘못된 `period`는 `CoreException(BAD_REQUEST)` → 400, 미지정 시 기본 daily로 **기존 API 하위호환**을 유지(회귀 테스트로 확인).
- **`rank`는 MySQL 8 예약어** — 컬럼명으로 쓰면 DDL이 실패해 자바 필드는 `rank`, 컬럼은 `rank_no`로 매핑했다.
- **앱 분리 구조**: streamer / batch / api가 각자 도메인 사본을 갖는 컨벤션이라, MV 엔티티도 batch(쓰기용)·api(읽기용)가 같은 테이블을 각자 매핑한다. 공용 모듈을 새로 만들지 않아 배포 독립성은 얻되, 같은 개념의 사본이 늘어 변경 시 동기화 부담이 생긴다.
